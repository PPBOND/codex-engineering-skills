# 图解式工作汇报

## 用户确认的默认版式

1. **成果总览**：标题说结论，展示有依据的数字与前后对比，并标明适用范围、周期和截止时间。
2. **核心改造**：关系图或改造前后图，解释为什么值得做；箭头表达实际关系，不把独立事项串成顺序。
3. **收益与验证**：实测结果、正确性证据、内存等代价；没有性能对照就展示已有验证，不造百分比。
4. **交付路线**：实现、验证、发布等阶段；阶段不等于时间，不估造日期和完成率。
5. **工作全景图**：全部工作按主题分组，每项有图、有解释，默认可见。
6. **问题处理图**：每条展示“问题 → 已做处理 → 当前状态/下一步”，默认可见；分类数量不是缺陷关闭率。
7. **会话与证据**：完整证据表、问题原始说明、来源会话可折叠；点击图中证据能定位并展开。

简短周期允许合并章节；全量工作、问题和来源不能遗漏。分组与数量由当期账本确定，不固定沿用示例的 18 项或 11 项。其他事项独立列示。

## 工作全景图的解释深度

每项默认显示四个字段，各用 1–2 句，按实际复杂度调整，不追求把文字压成几个词：

- **原来问题**：什么不方便、不可靠或有成本，为什么要做。
- **具体改动**：实际改变的行为，或完成的研究/验证；用日常语言解释技术词。
- **带来价值**：对性能、可靠性、维护或交付的意义。有证据才写量化收益，研究目标与实际收益分开。
- **当前状态**：实现、验证、提交、发布到了哪一步，还有什么限制；不能只写“通过”。

图放在解释附近，采用前后对照、汇合、分支、嵌套或阶段链。标题面向结果；函数名、提交号和长测试条件放入证据。图与文字互补，不能用“数据 → 编码 → 结果”代替背景和价值。

先让读者知道“交付的到底是什么”：工具优化、功能实现、接口重构、测试或设计。标题采用“具体对象＋动作”，图中保留该对象；正文回答“输入什么 → 自动/人工做什么 → 输出什么”。例如日志排查应明确写“Python 日志自动排查工具优化”，而不只写“跨层关联”或“问题定位能力”。保留工具实际支持范围，不暗示能自动找出所有问题的根因。

有对应证据时，可以这样写：“优化 Python 日志自动排查工具，按数据库实例和数据 key 自动筛选日志，检查写入、读取及重启恢复过程，输出发现的异常和日志行号。开发人员可直接查看异常及相关记录，减少人工逐行查找。”状态写明哪些工具测试和实际日志验证通过、是否提交；具体数字从当期证据取，不沿用示例。

### 写作对照

以下用于说明表达方法，不是固定项目清单；名称、动作和结果必须来自本期证据。

| 容易让人猜的写法 | 更明确的标题 | 正文应补的信息 |
|---|---|---|
| 跨层关联、定位能力提升 | Python 日志自动排查工具优化 | 输入哪些日志，自动检查什么，输出异常及哪些定位信息 |
| 校验和收敛 | FlexDB / FrostKV 数据校验算法统一 | 原来两套实现，这次统一了什么；局部计算快多少，整库是否测过 |
| 回收闭环 | 旧索引文件自动清理修复 | 什么情况下文件会积累，改后如何触发清理，用什么测试验证 |
| 调度能力建设 | 多数据库实例共享调度器设计 | 设计要解决什么问题，哪些文档已完成，代码是否实现 |
| 流程可视化 | 数据库架构与核心流程动态图制作 | 交付哪种可查看材料，能看哪些流程，剩余图是否完成 |

写作顺序：先确认交付物和事实，再选择图形，最后润色。效果词不能代替对象，漂亮图也不能代替解释。摘要、图中文字、工作卡和问题图使用一致名称。背景没有证据时写需求或验证目的，不倒推出原系统一定有缺陷。

示例写法（不代表本期事实）：“数据落盘前要先生成中间镜像，再复制到最终记录。此次直接生成最终记录，并调整批量提交方式，减少数据搬运与底层写入。固定负载已观察到耗时下降，但峰值内存增加；最终交付版本还需统一验收。”可配改造前后三步/两步流程，量化结果另取证据。

桌面卡片通常两列，手机单列。正文约 14–16px，次要注释不小于 12px。高度随解释展开；四个字段默认可见，不能裁切、折叠或为了凑卡片缩小字体。

## 视觉与实现

采用已确认的图解简报风格：白底、深蓝正文、青绿成果、橙色待推进事项、紫色虚线表示设计/候选。整页约 1280px 宽，系统中文无衬线字体，分节留白。用户另选风格时按其新要求。

`assets/report.html` 是无业务数据的离线起点，复制到报告目录再填充；不要修改技能模板来存放当期证据。对已存在的报告，优先保留其风格，不强行套版。

- 不依赖 CDN、网络字体或外部脚本；CSS/JS 内联。所有正文在 HTML 中，即使禁用脚本也能读。
- 模板里的 `{{...}}` 均需替换。复制图文项时更新稳定 ID 和来源链接。模板条形宽度必须按实测数据计算，没有数据则移除图。默认展示全部工作，不要求读者先筛选。
- 动态填入的文本需 HTML 转义；链接只采用已核实的来源，并检查协议，禁止把历史消息直接当 HTML 或脚本插入。
- 图表只表达同口径关系并带原始数值表，不能用装饰进度条暗示无证据的完成率。模板不预造性能图。
- 目录锚点和证据编号唯一且可达。会话链接按应用返回的类型/链接处理；不为未知来源猜造 URL。
- 打印须展开风险和所有筛选内容，结束后恢复原状态。新增分页图表/隐藏面板时一并纳入打印验证。
- 页面使用明确的按钮文字、可见键盘焦点、表头、语义章节；不能只靠颜色表达状态。

## 输出与检查

在现有 reports 根目录按周期建立独立目录；无既有约定时使用用户文档目录的 `Codex/reports/YYYY-MM-DD_DD`。不要覆盖别的周期或原始材料。HTML 默认交付；只有用户需要或已有配套时才附 Markdown/证据清单，并保持内容一致。

按风险检查：

- 数据：覆盖清单、工作项、风险数量、证据编号、日期和统计一致；无占位符或上期残留。
- 页面：在 320、390、768 和桌面宽度检查，无横向溢出、截断或重叠；用截图检查真实呈现。
- 交互：筛选与计数准确、空结果正常、展开收起有效、锚点正确、无脚本错误；打印显示所有内容并能恢复。
- 内容：数字、单位、性能方向、测量快照和验收范围一致；仅本次整理未重新跑项目测试时要说清。逐项做陌生读者检查：不打开证据，能否说清为什么做、改了什么、有何价值、还有什么没完成？不能就补解释。
- 全文检查，而非只改用户举出的例子：标题、摘要、图中标签、工作说明、问题图都要点明具体对象与动作，区分代码改动、工具优化、测试、设计和调研。“实调、收敛、闭环、底座”等简写按上下文换成“实际调用验证、旧文件可回收、整套流程跑通、具体模块”等准确表达；保留必要技术名并解释其作用。
- 状态检查：测试结果必须带验证对象。例如“Python 工具测试通过，并用实际读写/正常重启日志验证”与“数据库断电恢复通过”是不同结论。未测的边界放在对应状态或证据里，不用无关免责声明冲淡成果。

用可用浏览器或已有 Playwright 环境检查，不为简单报告额外安装前端框架。无法执行某项检查时如实报告。成功后用应用文件面板打开最终 HTML，并在答复中给绝对路径链接。

维护技能模板时，可用已有 Node + Playwright + Chrome 执行 `scripts/check_template.cjs`。它检查图文默认可见、四项解释、证据展开、打印恢复、锚点及四档视口并输出临时截图路径；不能代替当期事实核对。
