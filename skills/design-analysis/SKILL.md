# 详细设计分析（Design Analysis）

从高层需求出发，通过代码分析、竞品调研和与用户的迭代确认，输出完整的详细设计文档。

## AI 读法约定

> **规则标签**：
> - `[必做]` — 硬约束，省略会阻塞下游或导致返工
> - `[推荐]` — 默认执行；不适用时文档一句话说明理由即可跳过
> - 无标签 / *斜体例子* — 参考模板，按需采用
>
> **产出文档倾向**：表格 > 列表 > 段落；**结论 > 阐述**；能引用上游章节就不复述。
>
> **长度预算**（参考）：analysis 主文典型 ≤ 800 行(附录不限）；超过时 P5 先做物理收敛再继续。

> **前置加载**：开始设计前先加载项目 arch-constraints skill（分层模型、线程模型、内存模型、规格常量、设计倾向性、RPC 估算模板）。
>
> - 分布式存储项目：执行 `$distributed-storage-arch-constraints`
> - 其他项目：使用现有项目架构约束；没有专用 Skill 时从 AGENTS.md、代码与设计文档提取相关约束，不要求先创建 Skill 才能分析
>
> 下文的接口、缓存、分片和事件循环术语均为通用示例，实际名称必须从目标仓库验证。

## 核心原则

1. `[必做]` **代码验证优先 + 架构事实先验证再做方案**：对现有系统的断言、方案依赖的前提都必须用 grep/read/explorer sub-agent 先落实到 file:line。事实没确认就设计，方案会被反复推翻（典型症状：评审时方案被拆穿"你假设 X，但代码其实是 Y"）。需要落实的前提至少包括：
   - **架构事实**：跨节点边界、ID 重用策略、字段是否存在、父子关系是否 denormalized
   - **数据源粒度**：上游 metrics / 数据源的标识符粒度和本次需要的粒度是否一致（per-file vs per-gateway vs per-cluster 错位是常见坑）
   - **线程模型兼容**：polling 线程不能用阻塞式 API；需要 TLS / atomic / lock-free 的场景先确认
   - **消费方枚举**：Hook 点不只查主调用方，还要枚举其他 gateway / protocol adapter / test harness（例如公共 SDK 同时被 CLI、网关和测试工具使用）
2. `[必做]` **决策透明**：存在实质取舍时比较可行方案并说明推荐；已有已批准方案或只有一个符合约束的方案时直接沿用，不为满足数量制造替代方案。
3. `[必做]` **量化**：内存（struct layout）/ 延迟（ns 级）/ 精度（公式+数值）/ 代码量（参考基线）/ RPC 量（代入真实集群规模）
4. `[必做]` **信息来源标注**：📄 代码/文档确认 / 🔍 架构推测（给推测链条）/ ✅ 已决策 / ⚠️ 待决策
5. `[必做]` **用户质疑时不辩护**：回到代码和证据重新推演，不要为旧方案辩护
6. `[推荐]` **Mermaid 时序图**：核心设计章节的数据流 / IO 路径 / 状态机传播配时序图（兼容飞书渲染）
7. `[推荐]` **不做过度防护**：评估触发概率和代价；罕见场景可接受"已知限制 + TTL 自愈"（例如逐项 generation 校验的成本远高于罕见 ABA 风险）
8. `[必做]` **状态与范围先固化**：有状态或跨模块设计必须先写 state/truth source、lifecycle events、scope commitment，再写具体实现方案。

## 流程总览

六个 Phase：**P1 输入与背景**（需求 + 竞品）→ **P2 架构设计**（迭代式 + 完备性体检）→ **P3 缺陷与细化**（缺陷分类 + 子组件 + 时序图）→ **P4 规格估算**（内存 + RPC + 代码量）→ **P5 设计自检收敛**（硬门禁）→ **P6 文档管理**（章节组织 + 下游引用契约）。

## Phase 1：输入与背景

### 1.1 需求分析与代码探索

1. **读取需求文档**：核心要点提取到结构化表格
2. **探索代码模块**：默认由主 agent 按依赖阅读；多 Agent 已获授权时才委派独立模块，不因缺少子 Agent 阻塞分析
3. **构建能力矩阵**：`需求 | 现有能力 | 复用 | 新增`
4. **识别关键设计约束**：从代码提取架构约束（分片模型 / 一致性模型 / IO 路径线程模型）
5. `[必做]` **枚举所有消费方**：Hook 点或数据源必须确认**谁在用它**——不只当前场景的调用方，还有其他 gateway / plugin / test harness

**探索重点**：数据结构（struct layout）/ RPC 接口 / 持久化格式 / **线程模型**（polling / coroutine / thread-pool）。需求文档有模糊点在此阶段标注，不要等到设计阶段才发现。

### 1.2 范围声明（硬门槛，三件事都必须写清）

从用户需求和已批准决策提取范围并写入文档头部；已明确的范围无需重复确认。仅对会改变本次交付的未决范围选择请求确认并暂停依赖内容，其余分析继续。三件事必须写清：

- **本次做什么**：当前分析文档要详细展开的功能
- **本次明确不做什么**：已讨论过但本轮确认不做的（含"首期裁剪"的功能）
- **后续大交付做什么**：已识别但延后的**产品级能力**——只登记标题和一句话意图，不在正文展开

后续 Phase 发现范围变化时必须回来更新此声明；若"后续大交付"条目在本次被拉进正文，必须先升级为"本次做什么"或停止展开。

**交付阶段的层次**（重要）：
- analysis / swdd 只感知**大交付阶段**——产品/版本级别的交付划分（"本次 A+B+C 一把交付"和"后续 D+E+F"）
- analysis / swdd **不需要感知** spec 内部的编码实现阶段划分
- 整体一把发布时，analysis / swdd 正文**不要保留内部阶段标注**——去阶段化
- 编码阶段的划分归 spec 负责；评审视角（SWDD）和设计视角（analysis）都只看大交付

### 1.3 竞品分析

1. **搜索竞品**：本地文档仓库 / 内部前代产品代码 / 行业调研
2. **对每个竞品提取**：架构模型 / 实现机制 / 已知限制 / 特色设计
3. **区分信息来源**：📄 代码确认 vs 🔍 架构推测（标注推测理由）
4. **构建多维对比表**：至少覆盖功能 / 精度 / 性能 / 一致性模型

**要点**：
- 已有产品能力的分析优先于外部竞品——先看目标仓库的前代或相邻实现，再看外部
- 对内部产品直接读代码，提取关键函数 / 数据结构 / 处理流程
- 推测时给出推测链条（"因为 A 📄 + B 📄 → 推测 C 🔍"）

**篇幅上限**：
- 主文档内**至多 3 个竞品**详细对比，其余一句话带过
- 单个竞品描写超过 ~150 行，抽到独立 `docs/design/<module>/<feature>_research.md`，主文档只留"已调研 / 结论 / 链接"
- 目标：主设计文档服务**决策**，不是资料库

## Phase 2：架构设计

### 2.1 迭代式设计步骤

1. **提出初始架构**：组件职责表 + 数据流向图（mermaid）+ 关键数据结构
2. `[必做]` **对实质取舍给出方案比较**；影响公开语义、一致性、持久化、兼容性或交付范围且尚未决策时，请用户确认。常规内部实现选择说明理由后推进；用户要求逐点审批时按其要求执行
3. `[必做]` **承诺级别标注**：区分"服务端强约束"（如写入路径硬拦截）与"体验层能力"（如客户端预检），从源头消除下游 SWDD/Spec 的歧义
4. **用户质疑时**：回到代码验证相关前提，修正有证据的问题并继续；只有仍缺关键决策时才暂停依赖部分
5. `[必做]` **方案被否后列根因**：典型方向（持久化派生属性 / 全局广播 / 响应字段搭载）被否后，写一句话记录根因（更新代价 / 订阅复杂度 / 后台组件压力 / 外部输入不可信等），在新方案明确避开

### 2.2 关键设计模式

- **复用优先**：先检查现有能力，在其上加 enforcement / extension
- **Lazy Cache**：低频映射关系首次 miss 时 resolve 并永久缓存
- **Hook 点选择前先枚举消费方**：覆盖公共 SDK 的 CLI、网关、协议适配器和测试工具等所有调用路径
- **双层检查**：Client 乐观预检 + Server 权威校验

### 2.3 项目级设计倾向（引用）

**项目特有的设计偏好（倾向、规模参数、典型风险、RPC 估算模板、典型时序图类别、典型盲区）放在项目 arch-constraints skill 里，不在本通用流程重复**；分布式存储可使用 `$distributed-storage-arch-constraints`。

流程上的要求（项目无关）：
- 方案对比的推荐项需和项目 arch-constraints 声明的倾向一致；相反需显式论证
- 方案被否后在"决策跟踪"记一句话根因（更新灾难 / 广播复杂度 / 时钟不可信等）

### 2.4 完备性体检（方案成型后必做）

主方案定稿前，用以下 4 条短清单防疏漏。**每条必须给出具体文档证据（"在 §X 写了 Y"）**；不适用写"不涉及 + 原因"，不能空过。

> 本清单只覆盖"事前容易遗漏"的维度（前提验证 / 视角覆盖 / 扩展性 / 核心风险）。时序图覆盖 / 可观测可测试 / 交付兼容性留给 P5 事后自检，避免重复打卡。

| # | 维度 | 检查问题 | 不通过的典型症状 |
|---|------|---------|-----------------|
| 1 | **架构前提已验证** | 所有关键架构前提（跨节点边界 / ID 重用 / 字段存在性 / 父子关系粒度等）是否都引用了具体代码位置或 explorer sub-agent 报告？ | 方案假设"应该是这样"却没落实到 file:line；后面被拆穿会重新来 |
| 2 | **多视角数据流齐备** | 从本方案涉及的每个参与方视角（分布式：Server / Client / 管理面；单机：模块 A / B / C；业务：actor 1 / 2 / 3）各自过一遍数据流，消费方视角是否全覆盖？视角之间的交互是否独立成章/成段？ | 只写了主视角，其他视角怎么用留空 |
| 3 | **扩展性 N+1** | 加第 2 个同类特性时本方案要不要重写架构？三个子问题缺一不可（详见表下） | 单特性看完美，加第 2 个同类特性时要重写架构（命名通用化解决不了形态问题） |
| 4 | **核心风险都有决策** | 本方案暴露的每项核心风险（项目 arch-constraints 的"典型风险"章节 + 本功能特殊点；分布式场景常见的 ABA / 时钟 / 传播延迟 / 冷启动 / 热点）是否都有方案（+代价量化）或显式已知限制？ | 某项未在文档提及（= 未想过） |

**第 3 项「扩展性 N+1」三子问题**（任一命中即必须先抽 feat-agnostic 基础设施再做单特性，反模式详见 §4.1）：
- **(a) 同类特性枚举**：已知 / 已规划的同类特性有哪些？至少枚举 3 个；spec 预留位 / 命名相近 / 注释 "TODO: future" 都算
- **(b) 边际成本量化**：K 个特性同时存在时，本方案的接口字段 / RPC / 消费方流程边际成本是 O(1) / O(K) / O(K²)？响应搭载、字段一一对应、消费方流程"复印 N 份"通常是 O(K) 警报
- **(c) 数据流绑定**：客户端数据流是否绑定在某个特性的具体字段？典型反例：响应搭载 `<feat>_color` / 客户端 cache `color_to_<feat>_id` 一一对应 server 响应

**执行方式**：P2 末尾写体检表（同上列），填具体证据；通不过的条目阻塞 P3。4 条是本流程反复吃过亏的"视野盲区"维度。

### 2.4.5 Stateful / Cross-Module 设计必备清单

只要涉及持久化字段、proto/enum/feature bit、runtime cache/allocator/scheduler、RPC、client/server 传播或生命周期清理，就必须在 analysis 主文中提供以下表格，作为后续 SWDD/spec 的输入。

1. **State and truth source inventory**

   | Fact / state | Truth source | Cache | Owner granularity | Reader paths |
   |---|---|---|---|---|

2. **Lifecycle event inventory**

   | Event | State update | Clear path | Observable result | Failure behavior |
   |---|---|---|---|---|

3. **Scope commitment table**

   | Capability | Current MR | Follow-up | Out-of-scope | Not a dependency | Notes |
   |---|---|---|---|---|---|

4. **Alternative rejection table**

   | Decision | Selected design | Rejected alternative | Rejection reason | Why it still holds |
   |---|---|---|---|---|

硬规则：follow-up 只能在范围声明和后续规划中出现，不能被写成当前验收或系统依赖。

### 2.5 方案评审（主方案级变更后）

> §2.4 检查完整性，§2.5 从需求、架构约束、风险和替代方案重新审视主方案。评审职责必须完成；独立 sub-agent 只在多 Agent 已授权且可用时使用，单 Agent 模式由主 agent 按同一清单复审并如实标注自审。

**触发条件**（任一即触发；不要每个小迭代都跑）：
- 主方案首次成型（§2.4 完备性体检通过后）
- 主方案大改后（核心组件职责 / 数据流 / 接口形态变更，不是细节调整）
- 转 spec / SWDD 前（P5 核对评审证据；已有针对同一方案的有效评审可复用）

**调用方式**：多 Agent 已获授权时使用可用的独立 reviewer；否则主 agent 执行以下评审清单，不要求用户为满足本步骤开启多 Agent。

**调用模板**：

```markdown
独立架构评审任务。你是独立评审 agent，不参与方案创作；目的是用第三方视角发现盲区。

## 评审方法论（必读）
执行前先加载 $design-review skill，按其方法论推进：
- §一 4 层 checklist（现状对齐 / 文档一致性 / 漏洞排查 / 可操作性）
- §二 找漏洞 7 角度（状态机 / 时序 / 粒度 / 真相源 / 冷启动 / 失败 / 业务语义）
- §三 措辞信号映射表（"立即生效"、"接力 1-3 次"、"靠 TTL 自愈"… 等模糊词追问点）
- §六 输出格式（P0~P3 分级 todo list）

## 输入材料
1. 当前 analysis 文档：<docs/design/.../<feature>_analysis.md>
2. 需求/输入材料：<PRD / 用户原始需求文档路径>
3. 项目 arch-constraints：<项目 skill 引用，如 $distributed-storage-arch-constraints；或具体文档路径>
4. 决策跟踪表位置：analysis §3.3（**必读**，避免重提已被否的方案）

## 评审四象限（缺一不可）
1. **项目要求覆盖**：原需求每条逐项核对当前方案是否覆盖；标 ✅/⚠️/❌ + 文档段证据
2. **架构约束符合**：项目 arch-constraints 的倾向、规模参数、典型风险、典型盲区——本方案是否符合？相反/突破处是否有显式论证？
3. **设计合理性**：组件职责切分 / 数据流 / 接口形态 / 扩展性 / 复杂度是否相称问题规模；找隐藏风险
4. **替代方案**：至少提 1 个与当前主方案不同的设计方向；说明取舍。若无显著更优替代，写"主方案在当前约束下合理，无强力替代"——不要硬凑反对

## 输出格式（写到 <feature>_review_round_<N>.md）
### 1. 项目要求覆盖
| 需求条 | 状态 | 证据/缺口 |

### 2. 架构约束符合
| arch-constraints 条目 | 符合？| 证据/差异 |

### 3. 设计合理性 - 风险与盲区
- [P0/P1/P2] 风险 + 触发条件 + analysis 是否已识别（§X 或 "未识别"）
- ...

### 4. 替代方案
- 方案 A（当前主方案）vs 方案 B（你提出的）：5 行内的差异 + 推荐
- 或 "主方案在当前约束下合理，无强力替代"

## 必须遵守
- 评审证据必须落到 file:line / analysis §X / arch-constraints 段；散文化的"建议加监控/感觉不对"无效
- **不复述 analysis 已写的内容**；只写发现的问题、风险、替代
- 决策跟踪表 §3.3 已"否决"的方向不要重提（如已否决"全局广播"则不要重新建议广播）
- **不要直接改写 analysis** —— 你是评审，不是合著；输出落独立 review 文件
- 反模式与评审者守则参照 $design-review skill §七 / §九
```

**输出归档**：
- 路径：与 analysis 同目录，`<feature>_review_round_<N>.md`（N 从 1 起递增）
- review 文件不混入 analysis 主文，避免主文堆积评审痕迹
- 历轮 review 文件保留，便于追溯外部视角的演变

**反馈处理**：

| 评审条结论 | 处理动作 |
|-----------|---------|
| 重大问题（架构层 / 需求未覆盖） | 回 §2.1 重新迭代主方案；该轮 review 标"已触发重设计" |
| 中等问题（具体章节 / 决策细化） | 当前轮修补 analysis；review 该条标"已采纳：analysis §X 已更新" |
| 不采纳 | 决策跟踪表 §3.3 记一句话根因；review 该条标"不采纳：根因 X" |
| 替代方案被否 | 写入决策跟踪表"已否决方向"；后续轮 agent 评审时该方向不再重提 |

**反模式**：
| 触发场景 | 正确做法 |
|---------|---------|
| 每次微调都跑 agent → 上下文膨胀 / 用户疲劳 | 仅主方案级变更触发；细节迭代靠 §2.4 自检足够 |
| agent 综合性建议无证据（"建议加监控"） | 调用模板强制 file:line / arch-constraints 段证据；无证据条目可剔除 |
| agent 重提决策跟踪表已否决方向 | 调用模板强制让 agent 先读 §3.3；提了直接以"§3.3 已否决：根因 X"驳回 |
| agent 直接改写 analysis（接力创作惯性） | reviewer 输出独立结论；主 agent 在编辑授权和既有决策内吸收事实性修正，新重大取舍仍由用户决定 |
| 把 review 文件内容并进 analysis 主文 | review 永远独立归档；主文只反映采纳后的终态决策 |

## Phase 3：缺陷与子组件细化

### 3.1 边界场景探测

对每个核心流程问：跨边界操作？中间状态？极端并发？故障恢复？

### 3.2 缺陷分类（三类）

| 类型 | 定义 | 处理方式 | 示例 |
|------|------|---------|------|
| **产品缺陷** | 功能不满足需求 | 必须修复 | "不支持用户配置 burst 上限" |
| **架构缺陷** | 设计有结构性问题 | 必须修复或标注为已知限制 | 例如继承得到的策略键不一定等于最终执行目标 |
| **首期裁剪** | 功能完整但首期不做 | 标注"后续版本"，确认不影响架构 | "元数据 ops 限流首期不做" |

### 3.3 决策跟踪表

```markdown
### 已解决
| # | 问题 | 结论 | 章节 |

### 待决策
| # | 问题 | 优先级 | 可选方案 |

### 已知限制（不修复）
| 限制 | 量化 | 可接受理由 |

### 首期裁剪（后续版本）
| 功能 | 理由 | 架构影响 | 预留措施 |
```

### 3.4 子组件细化

对每个子组件：竞品对比 → 方案选择 → 数据结构 → **时序图（必须）** → 决策表。

`[必做]` **对依赖的现有数据源/功能必须验证**：
- 数据粒度是否匹配（per-file vs per-gateway vs per-cluster）
- 线程模型是否兼容（需要 TLS？atomic？lock-free？）
- 所有消费方是否都能获取（不只是主场景的调用方）

### 3.5 时序图选择原则

核心设计章节必须配时序图；**不是每个功能都套用同一套类别**（加密 / 压缩 / 纠错功能的关键流程和分布式 cache 截然不同）。按下列通用原则挑选：

1. **写路径 / 读路径 / 状态变更路径** 各至少一张
2. **正常路径 + 至少一张异常或降级路径**（RPC 失败 / 数据缺失 / 降级 fallback）
3. **初次 / 冷启动路径**（若涉及缓存 / 懒惰构建 / 持久化恢复）
4. **跨组件 / 跨层交互**：每一条跨边界的调用链都有一张
5. **配置 / 管理面写入流程**（若有管理面 API）

项目典型的时序图类别模板（如管理面 / I/O 热路径 / Cache 刷新 / 状态传播 / 冷启动 / 故障降级）维护在项目 arch-constraints skill。

### 3.6 跨组件状态同步（若本方案涉及）

**若本方案引入跨组件 / 跨层的状态同步**（client-server cache / 两侧 TTL 协同 / 多节点共识），该状态同步路径建议**单独成章**组织：

- 数据结构（容器字段 / entry 布局）
- 维护事件表（初始化 / 响应回传 / 触发 pull / TTL 过期 / 跨实例变更事件）
- 按选择原则列出的典型流程时序图
- 边界场景表
- 各侧状态持有方职责对比

若本方案没有跨层状态同步（纯业务逻辑 / 单机模块），此小节不适用。

### 3.7 盲区反写机制

P2.4 体检能抓住**已知的常见盲区**。但每轮分析都可能暴露新的盲区模式——这些模式不能只停留在本次对话，否则下一个会话重新踩。

**做法**：用户在方案迭代后期（3+ 轮之后）提出"这里应该改成 X / 这里缺 Y / 这里应该先 Z"时，先问自己：

> 这是决策变更（新信息下的合理调整），还是设计疏漏（前几轮根本没考虑到）？

**设计疏漏**按可复用性分流：

| 类型 | 落地位置 |
|------|---------|
| **通用模式**（其他项目也会遇到） | P5 收尾时建议用户：*发现通用盲区 X，建议追加到 design-analysis skill 的反模式表*；用户确认后 Edit 本 skill |
| **项目特定模式**（只在本项目架构下会出现） | 建议反写到项目 arch-constraints 的"典型盲区"或"设计倾向"章节 |
| **本 feature 一次性疏漏**（只和本业务相关） | 就在本次 analysis 的"已解决 / 已知限制"表里记录，不反写 skill |

**判定原则**：只反写"前几轮完全没考虑"的疏漏；"想过但选择另一方向"属于决策变更，归"已解决"或"已知限制"，不反写 skill。

**不生成 `_blind_spots.md` 这种旁文件**——下次会话不会有人去翻。让经验沉淀回 skill 本身才能被下次加载读到。

## Phase 4：规格估算

**规格估算合并为一个独立大章**（§规格估算），三个小节：内存 / 后台 RPC 量 / 代码量。不要散落在不同章节。

### 4.1 内存估算

精确到 struct layout，考虑 hash map overhead，给出典型+极端两个场景。

格式：`组件 | 单实例 | 实例数 | 集群总`。给出**本次** + **后续规划的额外量**（若有附录留档方案）两档数字，便于评审决策。

### 4.2 后台 RPC 量估算（必填）

`[必做]` **方案涉及新增 RPC / 响应字段搭载 / 跨节点批量操作时必填本节**。具体规模参数基线、三维度估算模板、典型风险清单见项目 arch-constraints；分布式存储可参考 `$distributed-storage-arch-constraints`。

通用要求（项目无关）：
- 按实际集群规模代入真实数字，不要停在"应该够用"
- 至少覆盖：节点间流量 / 客户端与服务端流量 / 响应字段搭载带宽 三类
- 附风险评估表，结论用一句话回答"能否接受"

### 4.3 代码量估算

区分新增/修改/测试，每个文件给参考基线（"参考 xxx.cc 895L"）。

结构：新增文件表（文件名 / 职责 / 预估 LOC / 参考基线）+ 修改现有文件表 + 测试代码表 + 汇总。

**只估算本次范围**；后续规划的代码量在附录留档，不进入本章汇总。

### 4.4 规模参数

具体数字代入项目 arch-constraints 的"规模基线"章节，叠加本功能特有参数（对象数量 / QPS）。不留在"应该够用"——具体数字才能暴露放大问题。

## Phase 5：设计自检（转 Spec / SWDD 前的硬门禁）

> 收到 3 轮以上反馈迭代后，或用户要求执行 `$design-to-spec` / `$design-to-swdd` 前，**必须先执行此步骤并收敛完成**，否则不允许派生下游文档。
>
> 派生下游前修复授权范围内的自检问题；只有当前交付依赖的重大未决项才阻塞相应内容，按 §5.3 分类推进，不因形式项或范围外标记停止整个任务。

### 5.1 文档收敛

**收敛信号**（触发时先做物理收敛，再进 5.2 一致性自检）：
- 文档超过 ~800 行
- 阶段定义或关键决策被重新划分
- "后续阶段"条目被逐步拉进正文
- 存在多份冗余章节（多版本内存估算 / 多份时序图）

**收敛步骤**：
1. 完整重读文档，逐章检查
2. 移除迭代讨论痕迹，只保留终态决策
3. 合并重复章节（如多份内存估算 → 保留最终版）
4. 确保 Changelog 反映最新状态
5. **阶段分离核查**：正文各核心章节只描述"本次做什么"对应的大交付；"后续大交付"仅在范围声明和附录摘要表中出现

### 5.2 多维自检清单

| 维度 | 检查内容 |
|------|---------|
| **内部一致性** | 决策表、架构图、数据结构、时序图中的信息是否一致？一处改动是否全文同步？ |
| **架构缺陷** | 每个 Hook 点是否覆盖所有消费方？依赖的数据源粒度是否匹配？线程模型是否冲突？ |
| **产品缺陷** | 需求文档的每条功能是否都有对应设计？标注为"不做"的是否有明确理由？ |
| **边界完整性** | Client 加入/退出/宕机？配置变更传播延迟？冷启动策略？异步上报公平性？ |
| **状态归属** | Stateful / cross-module 功能是否填写 state/truth source inventory？每个 state 是否有 update 和 clear path？ |
| **生命周期事件** | create/update/delete/unlink/reclaim/report/stats/cold-start/failure 是否逐项覆盖？ |
| **触点完整性** | feature bit / proto / RPC / cache hook 是否枚举所有 touchpoint，而不是只写主路径？ |
| **范围承诺一致性** | current MR / follow-up / out-of-scope 是否在 analysis 主文、附录、下游引用中一致？ |
| **规格验证** | 按极端规格重算 RPC/内存/CPU，是否有瓶颈？**RPC 风险评估表是否存在**？ |
| **时序图覆盖** | 按 P3.5 时序图选择原则覆盖（读/写/状态变更路径各一张 + 至少一张异常或降级 + 冷启动 + 跨边界调用链 + 管理面写入）？跨组件状态同步（若本方案涉及）是否独立成章？ |
| **待决策清零** | 所有 ⚠️ 待决策项是否已解决？ |
| **可观测性** | 关键状态变化 / 错误路径 / 风险窗口是否有日志 + metric 出口？限流 / 排队 / 错误是否有指标可观测？ |
| **可测试性** | 各类测试（单元 / 集成 / 长稳）分别覆盖哪些场景？是否存在"只能靠故障注入测"的 QA 盲区？ |
| **交付兼容性** | 升级路径 / 回退路径 / Proto 或持久化格式兼容性 / 默认行为破坏 是否都有答复？ |
| **范围漂移** | 正文内容是否超出 P1.2 范围声明？排除项是否误入设计正文？ |
| **交付层次一致性** | analysis 的阶段描述只停在"大交付"层；一次性整体交付的正文不应残留内部阶段切片 |
| **承诺级别** | 每个能力是否标注了"强约束"vs"体验层"？辅助能力（管理面工具）是否标注为"非系统依赖"？ |
| **过时术语扫描** | 重构后 grep 旧方案术语是否残留正文？（项目特有术语清单见项目 arch-constraints）正文"本次 vs 后续"表述是否一致？ |
| **章节编号连贯** | 章节挪动 / 合并 / 迁到附录后，原位置是否加了跳号说明？所有交叉引用 §X.Y 是否按新编号 remap？ |
| **后续规划集中度** | 后续规划章节是否都收拢在附录？主文不应出现详细的未来方案描述 |
| **完备性体检已填** | P2.4 末尾的 4 条体检 checklist 是否都填了具体文档证据（不是 yes/no）？任何一条卡在"不通过"都阻塞本 Phase |
| **方案评审已收敛** | P2.5 评审条目已分类处理且无重大未处理项？多 Agent 已授权时记录独立评审，否则记录主 agent 自审；不能把缺少委派当成设计不通过 |
| **盲区归纳** | 若反馈 3+ 轮出现设计盲区，是否按 P3.7 分类记录或提出维护建议？修改 Skill/arch-constraints 仍须明确授权，不把取得此授权作为本任务完成条件 |

**过时术语扫描清单**：旧数据结构名 / 旧流程词 / 旧 RPC 名 / 旧接口字段 / 旧阶段词（若已去阶段化）/ 旧 cache 类型名。具体术语清单由本次方案切换前后的词表决定；项目典型模式维护在项目 arch-constraints。

## Phase 6：文档管理

### 6.1 输出目标结构

按"入口 → 上下文 → 核心设计（连续） → 评估/周边 → 决策"的阅读路径组织。核心设计章节不要被评估 / 竞品打断。通用骨架：

```
§0  范围声明（本次做什么 / 本次明确不做 / 后续大交付做什么）← 硬门槛章节
§1  架构全景（顶层 flowchart + 组件职责）
§2  需求与产品决策（首期范围 + 与关联功能关系 + 决策总表）
§3  与现有体系的关系（复用什么、约束继承自什么）

── 核心设计（§4 起连续，按本方案实际需要选取） ──
§4  主数据流 / 核心算法（必含）
§5  跨组件状态同步（若引入 client-server cache / 多节点协同；独立成章）
§6  状态机 / 生命周期（若引入）
§7  存储方案（若引入）

── 评估与周边（接在核心设计最后一章之后，编号顺延） ──
      精度分析与竞品对比（至多 3 个详细竞品）
      应用层细节（面向用户可见的 API / CLI / 展示语义）
      规格估算（内存 / RPC / 代码量 —— 合并为一个大章三小节）

── 决策 ──
      待细化 / 已知限制 / 不在本次范围去向索引

附录 A、B、C …
  - 超长的前代产品 / 外部竞品代码级分析
  - 本次明确不做的功能方案留档
  - 替代方案留档（被否但保留参考的方向）
  - 后续大交付的功能方案留档
Changelog
```

*通用实例*：§4 配额继承链 / §5 Cache 与 I/O 流程 / §6 宽限期 / §7 配额持久化 / 附录 A 用户组配额 / 附录 B Credit 预授权 / 附录 C 权威分片执行 / 附录 D 默认配额。核心设计保持连续，后续规划整章迁入附录。

**章节顺序经验**：核心功能（存储方案 / 状态机设计）若被放在"精度分析 / 应用层 / 规格估算"之后，读者会先读完评估再回过头找设计，顺序就错了。优先把核心设计前移成连续段。若某章事实上成了后续规划，整章迁到附录；原位置加跳号说明"§X 已迁移到附录 Y"。

### 6.2 文档约束

1. 主文典型 ≤ 800 行——超过时收敛；附录可以长，正文要精简
2. 决策变更时全文搜索影响点，**Cross-reference 同步更新**
3. 竞品代码分析标注文件+行号
4. 持久化到 `docs/design/<module>/<feature>_analysis.md`
5. 所有文件引用使用项目相对路径

### 6.3 文档倾向

| 倾向 | 推荐做法 | 反例 |
|------|---------|------|
| **章节粒度** | 核心设计章节连续（§4-§7），评估/周边后置 | 核心章被精度/statfs/规格分析夹在中间 |
| **时序图数量** | 核心设计章有 ≥5 张 mermaid 时序图 | 只有架构 flowchart |
| **规格估算组织** | 独立大章，内存+RPC+代码量三小节 | 散落在不同章节 |
| **后续规划收拢** | 整章迁到附录，标题明确标"（后续规划）" | 主文每章都有"本次 vs 后续"小节 |
| **一次性交付 vs 多阶段** | 整体一起交付时，正文不再内部细分阶段 1/2/3 | 文档留着"阶段 1 做 X、阶段 2 做 Y"的历史标注 |
| **命名通用化** | cache / 接口可能被未来其他 feature 复用时，一开始就用通用名 + feature mask（例如 `ReactorFeatureCache` / `GetFeatureBits`） | 写死 feature-specific 后再重构 |
| **Changelog 组织** | 历史版本（v0.x~v2.x）每季度合并压缩一两行；近期变更逐条详细 | 逐条累积 40+ 行细节 |
| **飞书文档发布** | 参考 `feishu-doc` skill；大改重发新 URL，小改 append 勘误章节 | 多次 append 造成同名章节冗余 |

### 6.4 章节重排的实操规则

章节重排是高风险操作。操作前后要做：

1. **物理顺序变更**：切块 + 重排（用 Python 脚本分段切块，严禁手动反复粘贴）
2. **Heading 重编号**：`## X.` 和所有 `### X.Y` / `#### X.Y.Z` 同步（用占位符防止级联替换）
3. **Cross-reference remap**：`§X.Y` 全文替换（数字大的先替换，避免被数字小的吃掉；用占位符 token 绕过级联冲突）
4. **跳号说明**：原 §X 位置如不存在，加一行"§X 已迁移到附录 Y"
5. **Changelog 历史条目不追改**：保留原始编号（记录真实历史），正文才追改

### 6.5 下游引用契约（analysis 章节要便于被引用）

> 下游 SWDD 采用**引用式**而非复述式写作——SWDD 只写结论，详细推演 / 完整时序图 / struct layout / 规格推演过程都通过**引用 analysis 章节**呈现（不搬运原文；analysis 对评审可见）。因此 analysis 的章节组织要**便于被引用**：

- **章节标题反映内容类型，可定位**——好：`## Cache 链维护与刷新策略`；差：`## 关键设计`
- **时序图有独立 caption / 编号**，支持下游"引用图 X.Y"
- **关键数字放显眼位置**（表格 / 加粗行），不要埋在正文段落——SWDD 要摘取数字结论
- **每个决策落到一处**——理由不要散落在多个章节，SWDD 需要"一处决策 → 一个锚点"精准引用

### 6.6 下游文档协作边界

## 反模式

> 按**元类别**组织，跨项目复用。项目特定反模式维护在对应项目 arch-constraints 的"典型盲区"章节。

### 1. 证据不足（核心原则 #1 违反）
| 触发场景 | 正确做法 |
|---------|---------|
| 凭记忆断言现有代码 / Hook 点只查主调用方 / 依赖功能不验证粒度/线程/消费方 | grep/read/explorer sub-agent 先落实 file:line；消费方必须枚举到 gateway / 其他 protocol adapter / test harness |

### 2. 决策不透明（核心原则 #2 违反）
| 触发场景 | 正确做法 |
|---------|---------|
| 隐藏实质取舍 / 擅自改变已批准方案 / 被否方案不追根因 | 比较有实际差异的方案；未决重大选择取得确认，沿用已有决策不重复询问；被否记一句话根因 |

### 3. 边界不清（范围 / 承诺 / 分类）
| 触发场景 | 正确做法 |
|---------|---------|
| 范围漂移 / 当前与后续混写 / 一次性交付还分阶段 / 缺陷和裁剪混在一起 / 承诺级别不清 / 辅助工具写成硬依赖 | 范围变化时回更新声明；去阶段化；缺陷三分（产品/架构/首期裁剪）；每能力标强约束或体验层；辅助能力标"非系统依赖" |

### 4. 组织混乱（章节 / 命名 / 规格）
| 触发场景 | 正确做法 |
|---------|---------|
| 核心设计章被评估/竞品打断 / 规格估算散落 / 命名写死 feature-specific / 竞品当资料库堆砌 | 核心章连续（§4-§7），配时序图 + 状态同步独立成章；规格独立大章三小节（内存+RPC+代码量）+ RPC 代入真实规模；可复用名用通用类型+feature mask；竞品主文至多 3 个，其余抽独立 research 文档 |

### 4.1 接口形态绑定单特性（命名通用化解决不了的形态问题）

> 与 §2.4 体检表第 3 项「扩展性 N+1」对应：那里是事前体检维度，这里是已发生的反模式形态。

| 触发场景 | 正确做法 |
|---------|---------|
| 接口随 feat 数线性膨胀（每特性新 InodeAttr / Proto 字段、每特性 lookup/getattr 响应搭载、消费方流程"复印 N 份"） / 客户端 cache 一一对应 server 响应字段 / **第二个同类特性出现时镜像第一个特性而非抽公共层**（典型反例：dir_qos analysis 镜像 dir_quota 的 `nearest_<feat>_color` 模式） | **第二个同类特性出现 = 抽基础设施的最佳触发点**——发现 90% 镜像时先停下，写公共基础设施文档（feat-agnostic cache + bit mask 接口 + 双轨 RPC 等），再回头各自做单特性；接口先回答"feat-specific 还是 feat-agnostic"再决定形态 |

### 5. 过度防护（对罕见风险加高代价兜底）
| 触发场景 | 正确做法 |
|---------|---------|
| 罕见风险加高代价兜底保护（例如逐项 generation 校验 ABA 并触发级联失效） | 评估触发概率 vs 代价；代价大而触发罕见时接受"已知限制 + TTL 自愈"，在决策跟踪表中显式记录 |

### 6. 输出流程与文档卫生
| 触发场景 | 正确做法 |
|---------|---------|
| 未决重大选择被写成定论 / 3+ 轮不收敛直接派生下游 / 完备性体检走过场 | 按 phase 连续完成已明确内容，仅未决重大选择需要确认；~800 行或 3 轮反馈触发 P5 收敛检查，体检给具体证据 |
| 章节重排后交叉引用失联 / 过时术语残留正文 / 文件引用用本地绝对路径 | 重构后全文 grep 引用 remap；原位置加"§X 已迁移到附录 Y"跳号；Changelog 历史合并；文件引用用项目相对路径 |
