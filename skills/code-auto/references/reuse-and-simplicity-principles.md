# 复用、状态与简化原则

用于 `code-plan` 的方案设计，以及 `code-auto` 的实现、自审和 review。目标是在不牺牲正确性、性能、安全性和可读性的前提下，减少代码、隐式耦合与维护面。

这些原则是判断依据，不是机械配额。不要为了缩短函数而拆散一个内聚流程，也不要为了潜在复用而提前建立接口、工厂、继承层次或公共模块。

## 决策顺序

1. 需求是否真的需要代码；能否删除或通过配置/现有行为完成。
2. 仓库中是否已有可复用的实现、类型或模式。
3. 标准库或平台原生能力是否满足语义与性能要求。
4. 能否用局部、直接且最少的代码完成。
5. 只有存在当前调用方、真实变化轴或明确边界时，才新增抽象或模块。

## 实现原则

1. **单一责任**：函数或类型应承担一个内聚职责，并只有一个主要变化原因。优先提取可独立命名、测试或复用的逻辑；不要把顺序紧密、共享同一不变量的流程机械切碎。
2. **最小化共享状态**：优先通过显式参数传入所需值，通过返回值表达结果；优先无状态函数、自由函数或局部计算。不要把成员状态迁移成文件作用域或函数内的可变 `static`，后者仍是隐式共享状态。
3. **本地化副作用**：把日志、控制台、文件系统、网络、持久化和全局状态变更集中在清晰边界；核心计算尽量接收值并返回值。不要为了形式纯粹而绕开项目已有的事务、reactor 或生命周期边界。
4. **优先不可变对象**：构造时建立不变量，之后尽量使用 `const` 数据和只读访问。确需状态机或生命周期变化时，保留可变对象，但让合法转换、线程上下文和所有权显式可见。
5. **依赖窄能力而非具体大对象**：C++17 可选择自由函数、模板参数、回调或最小抽象接口；仅在确需运行时多态和可替换实现时使用虚接口。禁止为单个实现或假想未来实现创建接口。
6. **把原则应用到模块**：模块应职责明确、依赖最少、边界稳定，并避免重复。仅当拆分能降低现实耦合或形成真实复用时新增库/模块；不要把少量局部代码搬进新的 `utils` 层。
7. **组合优先于继承**：避免深层继承和为复用实现细节而继承。只有满足真实 `is-a`、可替换性和稳定运行时多态边界时使用继承。
8. **开发过程中验证**：选择能揭示缺陷的最小测试层级，优先验证可观察行为、边界、错误与回归场景。避免无断言测试、只复制实现逻辑的测试，以及紧耦合私有细节的脆弱测试。
9. **标准库优先**：在语义、生命周期和性能满足要求时，优先使用广泛理解和测试的标准库容器、算法、字符串、并发与资源管理设施，不手写替代品。C++ 代码仍必须遵守本 skill 的 C++17 限制。
10. **避免新增代码**：最好的维护代码是不需要存在的代码。优先删除、合并和复用；不添加未被当前需求使用的配置、扩展点、兼容层、依赖或防御分支。

## 阶段检查

每个 phase/stage 的 preflight、自审和 review 至少回答：

- 复用了哪些仓库代码、标准库或平台能力；新增代码为什么不可避免？
- 输入是否显式，共享可变状态是否已降到必要范围？
- 副作用、对象可变性和生命周期是否集中且清晰？
- 新接口、模块或继承是否有当前调用方和真实变化轴？
- 测试是否验证可观察行为并能捕获本次回归；是否存在可删除的代码或测试？
