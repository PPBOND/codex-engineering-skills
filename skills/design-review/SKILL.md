# Design Review

拿到设计文档（自己写的、他人写的、AI 生成的）做交叉评审，输出**分级 todo list**——而不是空泛的"看起来不错"。

适用产物：design analysis、SWDD、Spec、PRD、架构方案、技术选型对比文档。

## 触发场景

| 场景 | 备注 |
|---|---|
| `design-analysis` §2.5 触发的 agent 评审 | 主方案首次成型 / 大改 / 转 spec 前；按 design-analysis §2.5 的反馈分类处理 |
| 多轮迭代修订自己的设计 | AI 帮写 v1 后的二次审查；用户给"再看一遍"信号 |
| 评审同事 / 跨团队的设计文档 | 评审他人 PR / 设计澄清 |
| 路线切换后扫过期描述 | v1→v2 重写后扫残留旧术语 |
| 转下游前的盲区扫描 | swdd / spec 派生前的硬门禁前置检查 |
| Pre-Spec Gate Review | 用户要“转 spec / 写 spec / 从设计到实现”，或设计涉及状态、feature bit、cache、scheduler、RPC、生命周期 |

## 核心原则

1. **不替设计者决策**——把问题摆清楚、利弊量化清楚；最终选择由设计者做
2. **证据落地**——每个发现要落到 `§X / file:line / 表格行号`，不要散文化建议
3. **自我推翻的勇气**——上一轮提出的判断被纠正时，立刻承认、重推演，不为面子坚持
4. **不直接改写文档**——评审者不是合著者；输出 review 报告，让设计者吸收

## 一、4 层 checklist（从外到内）

每次拿到文档按这个顺序扫，每层卡住就停下来反馈，不要急着进下一层。

### L1：现状对齐（5 分钟）

**问题**：目标态 vs 当前实现态的对照。

**输出**：「已对齐 / 需补 / 已过时」三栏对照表。

**为什么先做**：再好的设计如果跟实现差太远，后面所有讨论都是空中楼阁。

**做法**：
- 找当前代码状态（git log / 现有 spec / 上一版设计）
- 逐项对比目标态
- 标记 `✅ 已对齐 / ❌ 需补 / ⚠️ 已过时`

### L2：文档自我一致性（10 分钟）

**问题**：同一概念在不同章节、不同文档里描述是否一致？

**checklist**：
- 文字描述 vs 代码示例
- 时序图 vs 表格
- 数据结构定义 vs 校验逻辑
- 已知限制 vs 时序图里的延迟数字
- 主文档 vs 引用文档（基础设施 vs 消费方）

**做法**：grep 关键术语，找自我矛盾。

**输出**：冲突清单 `| § | 现状 | 应改 |`。

### L3：决策合理性 + 漏洞排查（核心，时间最长）

按 §二「找漏洞 7 角度」+ §三「措辞信号」依次过一遍。

**输出**：漏洞清单（标 P0~P3）。

### L4：可操作性（落地前最后一步）

**问题**：Spec lint 红线、UT 等待原语、metric 是否能真落地？

**checklist**：
- DSL 红线 grep pattern 是否精确（避免函数定义自己 match）
- UT 等待异步事件是否给了 wait 原语模板（禁止 `sleep_for` 兜底）
- metric 阈值是否定义（不只是"加 metric"）
- 错误码 / 日志出口是否齐全

### L5：Pre-Spec Gate（转 spec 前必做）

触发条件：用户要求“转 spec / 写 spec / 从设计到实现”，或设计涉及状态、feature bit、cache、scheduler、RPC、持久化字段、生命周期。

检查项：
1. **State-owner check**：枚举每个 state/fact，写出 truth source、runtime cache、update events、clear events、reader paths；有 update 但没有 clear path 的按 P1 处理。
2. **Lifecycle event check**：覆盖 create/update/delete/unlink/reclaim/report/stats/cold-start/failure；每个事件对每个状态归属必须是 update / clear / no-op。
3. **Touchpoint check**：feature bit / proto / enum / RPC 必须列全声明、handler、fetch/cache、mutation hook、删除/回收、测试；部分接线未说明的按 P1 处理。
4. **Boundary/error check**：覆盖错误类型、根对象、外部 owner、越界、缺失、已解除关联和无效配置；分片 RPC 必须说明 owner-shard 校验策略。
5. **Runtime invariant check**：说明 COW commit boundary、published snapshot 一致性、overflow/saturation、cache notification order。
6. **Document drift check**：grep `已实现`、`已确定`、`bvar`、`NOSPC`、`NOTDIR`、`follow-up`、`TBD`、`待确认`；analysis/SWDD/spec 草稿里的当前范围、follow-up、out-of-scope 必须一致。

严重程度：

| 问题 | 转 spec 前严重程度 |
|---|---|
| 持久化 / 运行时状态缺 clear path | P1 |
| feature bit / RPC touchpoint 不完整 | P1 |
| 当前范围与 follow-up 矛盾 | P1/P2 |
| 重大需求没有测试映射 | P2 |
| 仅措辞或旧术语残留 | P3 |

## 二、找漏洞 7 角度

每次 L3 都按这 7 个角度依次过一遍。

### 1. 状态机角度
枚举所有状态 + 转换，找"卡死"路径。

*典型形态*：两个 cache TTL 不同 → A 已更新但 B 5s 内不会重新派生 → 卡在错误状态。

### 2. 时序角度
写出 T0/T1/T2，每步检查谁修改了什么状态、谁可能并发读。

*典型形态*：stale 期间结构变更（rename / delete）→ stale walk 沿旧链跑到错误位置。

### 3. 粒度角度
明确每个对象的粒度（per-process / per-mount / per-reactor / per-shard），找混淆。

*典型形态*：reactor 粒度的 cache 错挂在 per-shard 对象上 → N 倍实例化 + 跨 shard 不可见。

### 4. 真相源角度
同一信息在几个地方被缓存？TTL 是否一致？谁是权威？

*典型形态*：`has_<feat>` 既在 InodeAttr 又在 ChainSummaryCache → TTL 不同 → 抖动。

### 5. 冷启动 / 雪崩角度
稳态 OK ≠ 冷启动 OK。问"如果 N 个 client 同时 mount 会怎样？"

*典型形态*：lazy fetch 每次只前进 1 跳 → 16 跳深链冷启动需要 16 轮 IO 才收敛。

### 6. 失败路径角度
每个 RPC、每个 fetch 都要回答：失败怎么办？retry 多少次？backoff 怎么算？

*典型形态*：refetch 失败没 backoff → 形成快速重试循环。

### 7. 业务语义角度
相同的"漏拒/误判"在不同业务下容忍度不同。

*典型形态*：partial chain 漏拒——quota 偶尔超额可接受、immutable 漏写不可接受。同一基础设施服务多业务时要明确每业务的容忍度。

## 三、警惕的措辞信号

设计文档里这些词出现就要追问。

| 信号 | 隐含的问题 |
|---|---|
| "立即生效 / 0 延迟 / 同步" | 通常是想当然；追问机制（lazy invalidate？事件通道？） |
| "跨 shard 边界 / 接力" | 措辞背后语义不明确——owner_shard 判断？还是 cache 命中？ |
| "典型 1-3 次 / 一般来说" | 经验估算掩盖最坏情况；要求量化 worst case |
| "每加一个 feature 0 改动 / N 行" | 边际成本估算往往忽略业务侧差异 |
| "靠 TTL 自愈" | TTL 是兜底不是设计；问最坏窗口与体感影响 |
| "Future Work / 已知限制" | 严格审视——是真延后，还是掩盖未解决问题 |
| "参考 / 对齐 / 复用" | 通常引用旧设计但没确认是否还适用 |
| "应该 / 可能 / 大概" | 没量化的承诺；问具体数字 |
| "暂时 / 后续优化" | 落到决策表了吗？还是只是嘴上说说 |

## 四、判断方案最优性

**手法**：找替代方向，看否决理由是否站得住。

**好的设计文档会有这样的表**：

| 决策点 | 选定 | 替代方向 | 选定理由 |
|---|---|---|---|

**Reviewer 要做的**：
1. 否决理由是否过时（v1 时代成立但 v2 已变化）
2. 列表是否漏了某种方向
3. 是否隐含某个未声明的假设

**关键发现往往来自设计者澄清**：reviewer 可以提替代方向，但**最终决策应来自设计者对系统已有约束的理解**。Reviewer 不要硬塞自己的偏好。

## 五、多轮 review 工作流

每轮迭代节奏：

1. **第一轮：扫现状**——输出 L1 对照表
2. **第二轮：找冲突**——输出 L2 冲突清单
3. **第三轮：刨漏洞**——输出 L3 漏洞清单（P0~P3）
4. **第四轮：方案最优性**——输出替代方案 + 否决讨论

**每轮之间**：用户/设计者决策，调整方案。

**重要**：每轮修订后，**逐条核对上轮提的 P0/P1 是否落实**。用 `| 项 | 修订状态 |` 表格核对——这样不会漏修订，也不会让设计者重做已修的项。

**不要**每个小迭代都跑完整 review；细节调整自检即可。仅主方案级变更触发完整轮。

---

## 六、输出格式标准

每轮 review 报告应包含：

```markdown
## 一、整体评估
（哪些已对齐，确认上轮 P0/P1 的修订状态——逐条核对）

## 二、文档自我冲突清单（如有）
| § | 现状 | 应改 |

## 三、新发现的漏洞（标 P0~P3）
### 漏洞 X：{一句话标题}
**场景**：T0/T1/T2 时序
**问题**：{具体后果}
**修法**：{推荐方案} + {否决方案及理由}

## 四、值得讨论的更优思路（可选）
（提出 alternative，让设计者决策）

## 五、总结建议
| 优先级 | 项 | 改动量 |
（按 P0~P3 排序的 todo list）
```

**优先级定义**：
- **P0**：阻塞实现 / 文档互相矛盾 → 必修
- **P1**：语义正确性问题（漏拒 / 卡死状态） → 必修
- **P2**：值得做的优化 / 可观测性 → 建议
- **P3**：清理 / 措辞 → 可选

**改动量估算**：行数级别（"~30 行"）或工作日级别（"半天"），便于设计者判断采纳代价。

## 七、评审者守则（容易翻车的点）

### 1. 第一轮就要把"理解"对齐

Reviewer 的"误读"也有价值——能逼出文档里没写清楚的隐含假设。**不应该假装看懂**：明确说"我读到的是 X 语义"，让设计者确认。

### 2. 自我推翻的勇气

上一轮提出的判断被纠正时立刻承认、重推演。不要为面子坚持错误立场。设计者澄清意图后，很多"漏洞"会变成"文档没写清楚"。

### 3. 把"用户主动放弃的需求"写进背景

业务范围明确后，相应的"漏洞"严重等级要调整。不要把超出范围的需求当成阻塞项。

*例*：设计者明确说"immutable / encryption 不做"后，partial chain 在不同 feat 下容忍度差异这条漏洞**就消失了**。

### 4. 文档比代码更需要 review

如果代码本身已经过 spec lint / UT 检查，**~70% 的 review 发现是文档不一致 / 残留过期描述**，~30% 才是真正的设计漏洞。文档是后来实现者的真相源——文档错了，代码会跟着错。

### 5. 不替设计者决策

提出 alternative 时给数字、给取舍，**让设计者选**。reviewer 不应硬塞偏好。

*例*：UX 优化思路（如本 client local invalidate_all）reviewer 可提，但设计者基于"全集群对称性"取舍后选择不采纳——这是合理决策，记入决策表即可。

## 八、调用 sub-agent 评审（design-analysis §2.5 场景）

需要 agent 视角时，按 design-analysis §2.5 的"调用模板"调起 `general-purpose` agent。本 skill 的**方法论**作为 agent 评审的工作指南：

```
## 评审方法论（必读）
按本 skill §一 4 层 checklist 推进；
按 §二 7 角度找漏洞；
对照 §三 措辞信号映射表逐项扫；
输出格式按 §六。
```

**反馈处理**：见 design-analysis §2.5 反馈处理表（重大问题回 §2.1 / 中等修补 / 不采纳记决策表 / 替代方案被否归"已否决方向"）。

## 九、反模式

| 触发场景 | 正确做法 |
|---|---|
| 每次微调都跑完整 review → 上下文膨胀 / 用户疲劳 | 仅主方案级变更触发；细节迭代靠自检 |
| 综合性建议无证据（"建议加监控 / 感觉不对"） | 强制 file:line / §X / 表格行号证据；无证据条目剔除 |
| 重提决策跟踪表已否决的方向 | review 前先读决策跟踪表；提了直接以"§X 已否决：根因 Y"驳回 |
| 直接改写设计文档（合著者陷阱） | 输出 review 报告，由设计者决定是否吸收 |
| 把 review 报告并进主文档 | review 永远独立归档；主文只反映采纳后的终态决策 |
| 从训练记忆判断"应该是 X" | 永远落到当前文档 / 当前代码 / 当前讨论；记忆不可信 |
| 评审 N 轮还是同一批问题 | 每轮核对上轮修订状态；让设计者明确"已修 / 不采纳" |
| 把"设计者的取舍"当漏洞硬塞 | 用户已声明的业务范围 / 选定的对称性 / 接受的延迟，是决策不是漏洞 |

## 附：本 skill 与 design-analysis 的关系

| 维度 | design-analysis | design-review |
|---|---|---|
| 视角 | 设计者（从需求到方案的 6 phase） | 评审者（从已有方案找漏洞） |
| 输出 | 设计文档（analysis） | review 报告（独立归档） |
| 触发 | 从 0 写设计 | 拿到已有设计做审查 |
| 引用 | §2.5 引用本 skill 作为评审方法论 | 本 skill §八引用 design-analysis §2.5 调用模板 |

二者职责正交，主体内容只在各自 skill 中维护，避免重复。
