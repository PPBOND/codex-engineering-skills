# 从设计文档到实现规格（Design → Spec）

将概要/详细设计文档转换为 AI/Codex 可直接按阶段编码的实现规格文档。

## AI 读法约定

> **规则标签**：`[必做]` 硬约束 / `[推荐]` 默认做；不适用时文档说明跳过 / 无标签为参考。
>
> **产出文档倾向**：表格 > 列表 > 段落；结论 > 阐述；hook 点/API 引用 file:line > 复述实现。
>
> **长度预算**（参考）：spec 主文 P5 形态（实施 plan）典型 800~1200 行（含代码模板）；超过时先过 P4.2 四档自检，优先查"冗余"和"未清理"两档——这两档往往才是真正让篇幅膨胀的原因。**P6 参考态**（编码完成后瘦身）行数大幅缩短，但**不卡硬指标**——具体比例随 spec 复杂度 / 已交付 stage 数 / v2 增量保留量差异极大；用 P6.6 自检清单逐项打勾比纠结百分比更有指导意义。长期处于 P5 形态（不做 P6）意味着 spec 与代码 drift 是必然的。

**输入**：由 `$design-analysis` 产出的设计文档（`docs/design/<module>/<feature>_analysis.md`），或等效的详细设计文档。

**输出**：默认遵循仓库已有的 spec 目录约定；若无约定，优先 `docs/spec/<feature>_spec.md`，其次与设计文档同目录 `docs/design/<module>/<feature>_spec.md`。**生成前先 `ls` 仓库看是否已有 `docs/spec/` 或同模块的 spec 目录**，按现有惯例放置，不要硬编码位置。

**多阶段拆分**：主 spec 只承载"本次范围"的阶段；未来阶段必须拆分成独立文件 `<feature>_stage<N>_spec.md`，与主 spec 同目录。禁止一份 spec 同时承担"现在要做"和"以后再说"两种职责。

## 核心原则

1. `[必做]` **读者是 AI 编码 agent**——每阶段自包含（文件清单 + 代码模板 + 测试 + 验收命令）；设计文档回答"做什么、为什么"，Spec 回答"怎么做、做到什么程度"
2. `[必做]` **决策落实到 file:line**——不留模糊空间
3. `[必做]` **API 真实性 + 代码骨架完整**：代码模板调用的每个现有 API 必须有 file:line + 真实签名支持，禁止凭命名习惯猜。允许占位名，但必须在代码块前标"占位 → 真实 API"替换规则。类声明的每个公开方法要么给实现骨架、要么标 stub 或下阶段实现——AI 编码时不会回跳 analysis 找实现，"声明在 spec，实现回看 analysis"等于没写
4. `[必做]` **范围与边界**——主 spec 只写"本次范围"；未来阶段独立文件（或用户明确不提未来时直接不写）；管理面/辅助能力标"非系统依赖"，不与主路径混写
5. `[推荐]` **最小可交付开始**——阶段按独立可验证增量排序；高风险（IO 路径）放后面 + gflag 开关
6. `[必做]` **生命周期意识 + 锚点稳定性**——spec 不是写完就定稿。P5 形态服务编码 agent；P6 参考态服务 review / CI / future AI 接续。每 stage 编码完成就在该 PR 里走 P6 瘦身（删实施细节、保留契约/红线/决策）；瘦身时**禁止用具体行号**（`file.cc:123` 这种），只用"文件 + 类/函数/段名"——行号会 drift，符号名稳定。否则 spec 与代码 drift 是必然的

## 流程总览

六个 Phase：**P1 准入与范围锁定**（读设计 + 确认决策 + 范围）→ **P2 阶段划分** → **P3 文档输出**（结构、代码模板、各必备章节）→ **P4 双向校验**（反向更新设计 + 四档自检）→ **P5 代码风格规则对齐**（按项目 `.clang-format` / `.clang-tidy` 调整代码模板）→ **P6 实施完成后 spec 瘦身**（每 stage 代码合入后把实施细节转为 file:line 引用，保留契约/红线/决策档案）。

> **生命周期视角**：P1~P5 是"实施 plan 形态"；P6 是"参考态"。一份 spec 长期处于 P5 形态会导致代码模板与真实代码 drift；P6 是 spec 的退出态而非可选步骤。

## Phase 1：准入与范围锁定

> 转 Spec 前的硬门禁。未通过则停下来提示用户"先收敛设计文档再派生"。

### 1.1 准入检查

1. `[必做]` **完整读取设计文档**：提取所有终态决策（忽略讨论过程）
2. `[必做]` **`⚠️` / "待决策" 清零**：grep 搜残留；有则要求用户先确认
3. **文档已收敛**：无多份重复内容（多个内存估算 / 多个架构图）
4. **缺陷分类清晰**：产品缺陷 / 架构缺陷 / 首期裁剪已区分
5. **继承范围声明**：从设计文档 §0 提取三件事（本次做 / 不做 / 后续阶段），作为 Spec 阶段划分边界——"不做"和"后续阶段"均不进主 spec 阶段章节
6. **检查 SWDD 是否已存在**（`ls docs/design/<module>/<feature>_swdd.md docs/swdd/ 2>/dev/null`）：
   - 有 SWDD：读 SWDD 的**承诺级别表 / 错误码 / UT-X OB-X FS-X 用例编号 / 覆盖矩阵 / 产品需要确认项**；spec 直接继承这些清单，避免重复推导
   - SWDD 的"产品需要确认项"未结 / 存在 ⚠️ 待确认状态 → 阻塞 spec（同 ⚠️ 待决策处理）
   - 无 SWDD：走原流程（直接从 analysis 派生），spec 自己推导错误码和测试用例
7. `[必做]` **识别质量门禁触发条件**：只要涉及持久化字段、proto/enum/feature bit、运行时 cache/allocator/scheduler、create/update/delete/unlink/reclaim 生命周期、client/server 传播、cache TTL 或跨模块 RPC，就必须在 spec 输出 §Q 质量门禁矩阵。
8. `[必做]` **阻塞未收敛输入**：analysis/SWDD 中存在 `TBD`、`待确认`、`⚠️` 未决、或“当前交付 vs follow-up”矛盾时，不生成实现阶段；先列问题让用户收敛。

**未通过则停下来**：先执行 `$design-analysis` 的设计自检，输出修复方案让用户确认后再继续。

### 1.2 范围锁定

> 先锁定范围再写 spec。不在本次范围内的内容不能进主 spec，否则首版必返工。

1. `[必做]` **与用户逐条确认本次范围**：阶段编号、功能清单、承诺级别
2. `[必做]` **对齐 spec 阶段 = 本次做什么**：一一对应，不扩展
3. **未来阶段独立文件占位**：每个未来阶段一个 `<feature>_stage<N>_spec.md`，本次只写占位一句话（或用户明确不提未来工作时直接不写）
4. `[必做]` **辅助能力角色表**：

   | 能力 | 角色 | 说明 |
   |------|------|------|
   | 主路径组件 | 根本依赖 | 当前阶段必须实现 |
   | 管理面辅助（du、诊断） | 辅助能力 | 帮助判断，非系统依赖 |
   | 未来阶段功能 | 不进本 spec | 独立文件或不写 |

5. `[必做]` **承诺级别表**（与角色表并列）：

   | 承诺级别 | 含义 | 路径体现 | 典型形态 |
   |---------|------|---------|---------|
   | **强约束** | 系统硬保证，违反视为 bug | 硬编码；关键路径必配运行时降级开关 | 对外 API 的语义保证、持久化/一致性不变式、硬限额拦截 |
   | **体验层** | 内部机制/优化，不对外承诺具体数值 | 代码可改；可关闭不影响正确性 | 缓存命中优化、内部再分配、预检加速等"做了更好但关掉也能跑" |
   | **管理面** | 运维工具，非主数据路径 | 独立命令 / 异步接口 | 诊断命令、监控指标、运维查询 |

   **spec 阶段规划上的区别**：
   - 强约束路径 → 必须有 UT 硬覆盖 + 灰度回退方案 + 运行时降级开关
   - 体验层 → UT 覆盖状态机 + 行为合理即可；回退路径 = 关掉
   - 管理面 → 独立子节 + 标"非系统依赖"（见原则 #4）

   **常见陷阱**："产品不做 X 配置"（用户层承诺）≠ "系统不做 X 机制"（内部层实现）。前者限制的是**对外暴露给用户的配置字段**，后者限制的是**系统内部的实现策略**——两者并存不冲突。spec 阶段必须分清到哪一层，避免把"用户配置面不做"误读为"内部机制也不做"，反过来也一样。

6. **输出位置**：`ls docs/spec/ docs/design/<module>/ 2>/dev/null` 按已有惯例决定路径

### 1.3 待定决策确认（高频确认项）

从实践中提炼，设计文档通常不明确：

1. **存储位置**：集中式元数据服务 vs 分散到各分片或对象属性
2. **错误码编号**：查项目错误码定义确认编号规则
3. **Proto field number**：查现有最大值，直接追加
4. **CMakeLists.txt**：新增 .cc 加入 SRCS（不必问用户）
5. **RPC routing**：查现有类似操作的路由模式
6. **Hook 点所有消费方**：不只主调用方，还有 NFS / FIO / test harness
7. **IO 路径架构假设**（IO 路径功能必查）：查项目 arch-constraints 的**"IO 基线三问"**（上下文模型 / cache TTL 与失效机制 / 线程模型）；任一项未验证不要动工。三问的具体答案随项目而异（例如是否带 fd、cache 默认 TTL、是否跨 pthread），全部到项目 arch-constraints 查。
8. **项目标准组件复用**（避免自造轮子）：新增**统计 / cache / 定时器**前先查项目 arch-constraints 的**"标准复用组件清单"** + grep 项目现有基础设施；能复用就不自建。必须自建时在 spec §R 复用章节说明"为什么现有组件不够用"。
9. **flag 的产品语义 vs 技术副作用分层**：
   - 产品面描述用"这个 flag 开启什么能力"（用户视角，用产品术语）
   - 技术面描述用"这个 flag 触发什么副作用"（实现视角，用系统/数据结构术语）
   - **spec 代码注释里两者都写清**；避免长期把"副作用"当"主作用"编码，后续回头修正造成多轮返工
   - 常见错例：把"开启 X 能力"的 flag 注释成"用于触发 Y 内部机制"——产品语义丢失，评审或维护者会误解 flag 含义

### 1.4 从设计文档提取的信息

| 类别 | 提取内容 |
|------|---------|
| 数据结构 | struct layout（字段 + 大小）、存储位置、编码格式 |
| RPC 接口 | 请求/响应 message、service 扩展、错误码 |
| IO 路径变更 | Hook 点、线程模型、retry 机制 |
| 后台任务 | poller/scheduler、周期、触发条件 |
| 跨模块交互 | 数据流向、**所有消费方** |
| 已有代码复用 | 参考实现文件+行号 |
| SWDD 用例编号 | 若有 SWDD：UT-X / OB-X / FS-X 列表，用于 checklist 和代码注释追溯（见 P3 代码模板要求 #9） |

## Phase 2：阶段划分

### 2.1 划分原则

**从最小可交付功能集开始，逐步扩展**：

1. 每阶段独立可验证——明确验收标准和测试命令
2. 每阶段独立可发布——产品可选择"到此为止"
3. 高风险改动放后面——IO 路径修改排最后
4. `[必做]` **首期裁剪和未来阶段不占主 spec 阶段**——未来阶段独立文件；主 spec 的"后续阶段扩展点"只一句话标题 + 文件链接
5. 需求明确要求的功能不能放"可选"阶段
6. `[必做]` **管理面辅助能力（du / 诊断 CLI）独立子节**——不与核心流程混写；标"非系统依赖"

### 2.2 迭代路径

```
最小集（能跑通的核心链路）
  → 完善功能（边界处理、可观测性）
  → IO 路径集成（高风险 + gflag 开关）
  → [后续版本] 首期裁剪的功能
```

### 2.3 阶段模板

```markdown
## 阶段 N：标题

### 目标        一句话交付物
### 依赖        哪些前置阶段
### 文件清单    | 文件 | 项目 | 类型 | 行数 | 说明 |
### 代码设计    完整代码模板（不是伪代码）
### 测试与验收  编译运行命令 + 验收 checklist
### 评估        | 代码量 | 难度 | IO 路径影响 | 风险 + 缓解 |
```

> **代码量 > 1K 行** 继续拆分子阶段。

## Phase 3：Spec 文档输出

### 3.1 文档结构

```
顶部  IMMUTABLE CONSTRAINTS（红线表，最前置；放在 attention 最高位置）
顶部  Hosting Topology（持有者粒度表，紧随红线；spec 涉及新增持有实例时必填）
顶部  AI 编码前置 checklist（每次开始阶段必做的 grep 清单）
§0  范围声明（本次 = 阶段 1..N；未来阶段见独立文件清单）
§1  总览（决策表 + 阶段表 + 依赖图）
§Q  质量门禁矩阵（有状态 / 跨模块 / 生命周期复杂功能必填）
§2  公共定义区段（Proto + 错误码——阶段 1 一次性添加全部）
    §2.0   Module Boundary（接口契约速览；跨模块复用 / 阶段并行开发时必填——签名 + 语义，30 秒看完入口）
    §2.1+  Proto / 错误码主体
    §2.N   现有辅助 API 参考清单（file:line + 真实签名）
    §2.N+1 多层对齐表（flag/mask/bit 跨层对齐，若涉及）
§3  阶段 1 实现指南
§4  阶段 2 实现指南
...
§K  管理面辅助能力（du / 诊断 / 运维 CLI，独立子节，"非系统依赖"）
§L  跨阶段集成与故障测试（端到端 + INJECT + 长稳；与 SWDD UT 章节对齐）
§M  性能预算
§M+1 自检与潜在问题
§N  AI 编码常见陷阱（项目领域特有的易错模式 + grep 自查；本节存在时优先级 ≥ §M+1 自检）
附录 A：后续阶段扩展点（**可选**——每项：标题 + 一句话意图 + 独立 spec 文件链接）
附录 B：首期裁剪（保留为已知限制，说明后续如何补齐）
```

> **§2 区段编号约定**：§2 仅作编号分组，**不单独成 `## §2` 节**；区段内 §2.0 / §2.1+ / §2.N / §2.N+1 各自为独立 `## §2.X` 二级节。

### 3.1.5 §Q 质量门禁矩阵（触发时必填）

触发条件见 Phase 1.1。§Q 必须放在总览之后、实现细节之前，让后续编码和 review 先看到红线。

```markdown
## §Q 质量门禁矩阵

### Q1 Scope Freeze Table
| Capability | Status | Owner doc | Implementation in this MR | Notes |
|---|---|---|---|---|

### Q2 State Owner Matrix
| State / fact | Truth source | Runtime cache | Update events | Clear events | Reader paths | Test |
|---|---|---|---|---|---|---|

### Q3 Lifecycle Event Matrix
| Event | Persistent state | Runtime cache/state | Cleanup path | Client observable result | Required tests |
|---|---|---|---|---|

### Q4 Cross-Module Touchpoint Matrix
| Concept | Touchpoint | Required action | Verification |
|---|---|---|---|

### Q5 Boundary And Error Matrix
| RPC / handler | non-dir | root | foreign owner | out-of-range | missing | unlinked | invalid config | Test |
|---|---|---|---|---|---|---|---|---|

### Q6 Runtime Invariant Table
| Component | Invariant | Commit boundary | Failure behavior | Test |
|---|---|---|---|---|

### Q7 Requirement-Code-Test Triples
| Requirement ID | Behavior | Code touchpoints | Tests | Validation command |
|---|---|---|---|---|
```

硬规则：
- 重大需求没有 code touchpoint 或 test/validation 单元格时，该 stage 不可编码。
- Code touchpoint 必须写到文件 / 函数 / symbol；“接入 cache”“补测试”这类抽象描述不合格。
- OB/FS-only 必须说明为什么 UT 不适合，不能空着。
- follow-up / out-of-scope 不能出现在当前 MR 验收条件里。

### 3.2 AI 编码前置 checklist（顶部必备）

**作用**：AI 每次开始新阶段编码前，把"必须先 grep / 必须先对齐"的前提集中列清。

**模板**（具体 grep 命令见项目 arch-constraints；分布式存储可参考 `$distributed-storage-arch-constraints`）：

```markdown
> **AI 编码前置 checklist**：
> 1. grep 已用 flag bit / Proto field number / 错误码段（具体命令见项目 arch-constraints）
> 2. 通读 §2.N 现有辅助 API 参考清单
> 3. 若有 SWDD：checklist / 关键代码段带 `→ **SWDD XX-N**` 标签
```

### 3.2.5 Hosting Topology（**新增持有实例时必填**）

**触发条件**：spec 引入新的有状态实例（cache / scheduler / poller / reporter / coordinator 等），需决定"哪个类持有它、按 per-X 还是 per-Y 粒度"。

**为什么必填**：粒度错位是 AI 编码最难发现的错——代码可编译、UT 可通过、review 也容易漏。spec 反复说"per-X"但实现挂到 per-Y 类，编译期没有任何挡板。**唯一可靠的挡板是 spec 前置固化"持有者类 + 粒度"**——AI 实现前必须 grep 验证、reviewer 一表 diff。

**章节骨架**（紧跟 IMMUTABLE 之后、AI checklist 之前；属"红线"性质的前置约束）：

````markdown
## 🏗️ Hosting Topology（必读）

| 实例 | 期望粒度 | 持有者类（grep 验证已存在） | 持有者代码位置 | check |
|------|---------|----------------------|------------|-------|
| <实例名> | per-X | <候选类名 / grep 关键词> | `<file:line>`（grep 后回填） | <DSL 或 grep 命令> |

### 项目拓扑事实
- "X 和 Y 是不是同一概念"必须写明确，杜绝等价误用
- 多对一关系（1 个 X 跑多个 Y）：`X_id ≠ Y_index`
- 项目内常见的 "X≠Y" 错位配对从 arch-constraints 抄

### 等价错误（必须避免）
- `<X_id> = <Y_id>` ❌（两者不同概念）
- 把 <实例> 挂在 per-<错误粒度> 类的字段 ❌

### 实现前必做两步
1. grep 项目代码确认目标粒度容器是哪个类
2. **若不存在适配容器**：不要顺手挂到错误粒度的类凑合实现；停下来与需求方确认（新建容器 / TLS pattern）。设计意图明确是某粒度但项目层无对应容器，是项目层缺失，不能由实现层伪装。
````

> **填表义务**：spec 评审通过前，"持有者类"和"持有者代码位置"两列必须由实现者 grep 后回填具体值；未回填代表 hosting 风险未消除，**阻塞合入**。

**等价错误识别要点**（写 spec 时强制自问）：
- "X_id 和 Y_id 类型一致是巧合还是语义等价？"——类型一致 ≠ 语义等价
- "实现者能不能用 X_id 当 Y_id 假装通过编译？"——能 → IMMUTABLE 必须加红线 + 显式写 X≠Y
- "做成 per-Y 而非 per-X 会被哪个 UT 直接挡？"——找不到 → §L 缺一条粒度判别 UT

**check 列写法**：若项目已有 spec-lint 引擎，按其 DSL 写 check 列，让 CI 自动执行；否则用 backtick 包裹的 grep 命令作为人工或未来 lint 提示，避免散文化的"看一下 X 是否…"。

**关联强约束**：
- IMMUTABLE 表必须含一条"持有者粒度"红线 + 一条"X 与 Y 不等价"项目拓扑事实
- §L 跨阶段集成测试必须有**粒度判别 UT**（同 X 共享、跨 X 隔离两条对照用例），否则粒度错位无法 CI 化挡

### 3.3 §2.0 Module Boundary（接口契约速览，**跨模块复用 / 阶段并行开发时必填**）

**触发条件**（任一即必填）：
- 跨模块复用（消费方在其他 spec / 仓库，如基础设施 spec 服务多消费方）
- 阶段间需要并行开发（阶段 a/b 可并行的前提是契约冻结）

**目的**：消费方 / 跨团队 reviewer 第一关心"我能调什么、调了会怎样"，但 §2 详版（field number + 现有 API + 接入 N 步）密度过高、不适合 30 秒 review；速览节专门承担"边界先行"——契约冻结后消费方即可并行写接入代码 / 评审能不能用，不必等实现。

**位置**：§2 公共定义首节（§2.0），紧跟 §1 总览之后、§2.1+ 详版之前。

**速览 vs 详版分工**：

| 内容 | 速览（§2.0）| 详版（§2.1+）|
|------|------------|------------|
| 类对外公开方法签名 + 方法语义（≤ 3 行）+ 调用约定 | ✅ | ✅ 阶段章节展开 |
| RPC 名称 + 用途一句话 + batch 上限 + 错误码兜底 | ✅ | — |
| 跨模块 Callback / 钩子契约（签名 + 失败语义 + 调用约定）| ✅ | — |
| 消费方接入入口（一句话指引）| ✅ | — |
| Proto message 完整定义 / field number | ❌ | ✅（§2.1）|
| 现有辅助 API 参考清单（file:line + 真实签名）| ❌ | ✅（§2.N）|
| 消费方接入 N 步 checklist | ❌ | ✅（§2.N+M）|

**章节骨架**：

````markdown
## §2.0 Module Boundary（接口契约速览）

> 本节为冻结契约。修改任一签名 / 语义 = 阻塞并行开发的所有阶段，必须升级为正式变更（发起评审 + 同步消费方 spec）。
> 详细 Proto field number 见 §2.1；现有 API 引用见 §2.N；消费方接入 N 步见 §2.N+M。

### 类对外公开接口

```cpp
class <ClassName> {
  // <一句话职责>
  ReturnType public_method_a(ArgType arg);
  // 语义：<一句话>；失败：<返回什么 / 是否抛>；调用约定：<同步/异步、reactor 上下文要求>

  void on_event_x(...);
  // 语义：<一句话>；调用顺序约束：<如必须在 attr 落盘后调用>
};
```

### 对外 RPC（若 spec 引入跨节点接口）

| RPC | 用途 | batch 上限 | 错误码兜底 | 调用方 |
|-----|------|----------|----------|------|
| `<RpcName>` | <一句话> | <硬上限> | <超限返回什么> | <谁会调> |

补一段 2-3 行说清：请求路径 / 响应组装时机 / 灰度兼容机制（如 `supported_features` 字段）。

### 跨模块 Callback / 钩子契约

```cpp
using <CallbackName> = std::function<...>;
```
- 输入：<参数语义>
- 输出（回调）：<结果语义>
- 失败语义：<ok=false 时调用方应做什么；不该做什么>
- 调用约定：<同步/异步、是否在 reactor 上下文、是否阻塞 IO 路径>

### 消费方接入入口（一句话指引）

- <消费方场景 1>：调 `<api>(<args>)`，返回 `<result>`；详细 N 步接入见 §2.N+M
- <消费方场景 2>：...
````

**写作要点**（2 条判定准则；其余规则已被骨架 quote / 分工表自带）：

1. `[必做]` **每接口语义 ≤ 3 行**（参数关键含义 + 失败语义关键 + 调用约定关键）。**判定准则**：消费方在 30 秒 review 内必须知道才放速览，否则归阶段章节展开。展开的状态机 / 多步流程绝不进速览。
2. `[必做]` **签名 / 语义与 §2 详版 + 阶段章节代码模板一一对应**——内部矛盾（速览 `get_inode` / 详版 `get_inode_by_color`）让 AI 抓不准；P4.2 一致性自检挡这一档。

**长度上限**：单 spec 速览节 > ~150 行 → 拆独立 `<feature>_api_spec.md`，主 spec §2.0 只留入口链接 + 类摘要表（一句话职责）。否则速览自身违背"30 秒读完"初衷。

**关联强约束**：

- `[必做]` spec writer 在自己的 IMMUTABLE 表加一行红线：**"接口稳定性：§2.0 速览的签名 + 语义为冻结契约，修改阻塞合入；breaking change 走 §6.5 升级流程"**
- P6 瘦身阶段 Module Boundary 归入"永远保留"档（仅更新已交付符号名 / 删已废弃接口；接口需 breaking change 不属于 P6 瘦身，走 §6.5 升级流程）

### 3.3.5 §2.N 现有辅助 API 参考清单（必备）

**作用**：集中列 spec 代码模板调用的所有现有接口，避免 AI 按命名习惯猜 API（核心原则 #3 落地机制）。

**格式**：三列表 `调用目的 | 实际接口（file:line + 签名）| 使用说明`——spec 写作时按项目实际 grep 填入，不在 skill 预置示例（项目典型占位 → 真实接口对照表见项目 arch-constraints）。

**执行要求**：
1. 完稿前 grep spec 所有代码块，列出对现有类/函数的调用
2. 每项 grep 实际代码库定位 file:line；**未找到就不要猜名**——换实现方式或标"待定位 + 潜在隐患"
3. 同一 API 多次调用只列一次

### 3.4 §2.N+1 多层对齐表（按需）

**触发条件**：同一概念在多层有不同表示（持久化 flag bit + Proto enum mask + 缓存字段 bit）。若只一层不需要。

```markdown
| 层 | 字段 | 类型 | 作用 |
|----|------|------|------|
| 持久化层 | `StructA::flags & ATTR_X_ENABLED` | bit | 决定 encode 是否附加 X 段 |
| Proto mask | `FeatBit::FEAT_X = 0x01` | enum bit | RPC 请求中的 feature_mask |
| 缓存层 | `CacheEntry::has_x` bit 0 | uint8_t bit | reactor 本地缓存的当前值 |

**写入规则**：SetX 成功后 → flags |= ATTR_X_ENABLED → cache.on_x_set(...) 置 bit 0
**查询规则**：Client 只看 `has_x` bit；handler 按 mask 分支填
```

### 3.4.5 §R 复用既有基础设施章节（若涉及）

**触发条件**：本次功能复用其他模块已建组件（扩位 flag / 扩 Proto mask / 扩 RPC 字段 / 扩事件钩子 / 扩配置存储 / 扩 cache 等），而非新建独立子系统。

**目的**：让 AI 编码者一眼看清"哪些是复用 / 哪些是新建"，避免：
- 漏掉已有组件的并行改动点（如 cache 层的扩位、Proto 的 mask 扩展）
- 把"扩位改动"按"新建组件"的粒度写代码模板（冗余大）
- 复用组件的所有者信息丢失（评审时找不到共同维护者）

**章节骨架**（放在 §2 公共定义之后、阶段章节之前；具体内容按项目实际填写）：

```markdown
## §R 复用既有基础设施

### §R.1 被复用组件清单

| 组件 | 所在模块 spec | 本次改动类型 | 改动点 file:line |
|------|--------------|------------|-----------------|
| <组件名 1> | <其他模块 spec 路径> | <扩位 / 扩字段 / 扩事件> | <file:line> |
| <组件名 2> | ... | ... | ... |

### §R.2 并行所有者协调

| 复用点 | 原所有者 | 本次协作方式 |
|--------|---------|------------|
| <共享的数据结构 / Proto enum / bit 字段> | <原模块> | <本次占用的位置 / 是否冲突 / 评审要 @ 谁> |

### §R.3 复用点改动清单（diff 粒度，不重写实现模板）

> 每项只列增量改动，不展开整类实现。

- **扩位 / 扩字段**：<在已有结构哪里加 bit / 字段；encode/decode 是否变化>
- **事件钩子**：<在哪个 handler 成功后调哪个已有方法>
- **API 扩展**：<已有接口加分支还是新增接口；对称的已有实现在哪里>
```

**执行要点**：
1. 复用点必须给**精确 file:line**，不允许"参考 X 的实现"这类模糊引用
2. 扩位时先 grep**当前占用情况**（已用 bit / field number / enum 值），避免冲突；具体命令见项目 arch-constraints
3. "并行所有者协调"列表的作用是**评审召集**——把共同维护者列进评审圈，避免漏评审
4. 已有对称实现（其他 feature 先做过同模式改造）必须在 §R.3 里点出位置，spec 直接说"对称 X 做法"，不要重复推演设计方案

### 3.5 §L 跨阶段集成与故障测试（必备）

**作用**：端到端用例、INJECT 故障、长稳用例不属于任何单一编码阶段——需所有阶段组装后才能验证，独立成章。

```markdown
## §L 跨阶段集成与故障测试

> 各阶段 §3~§K checklist 覆盖本阶段内部独立验证；本章收敛跨阶段组装后的端到端和故障注入，并与 SWDD 的 UT、集成测试、故障稳定性表一一对应。

### §L.1 端到端主流程（OB-M / OB-N / ...）
  前置 + 操作步骤 + Checklist + SWDD 用例编号

### §L.2 灰度 / 升级兼容（OB-M）
### §L.3 故障注入（FS-1 / FS-2 / ...）  给出 INJECT 宏名和文件位置；宏未实现标"待实现"
### §L.4 长稳负载（FS-N）

### §L.X 覆盖矩阵
| SWDD 用例 | 覆盖位置 |
```

### 3.6 未来阶段独立 spec（若保留附录 A）

未来阶段单独建 `<feature>_stage<N>_spec.md` 时，结构同主 spec（范围声明 / 总览 / 公共定义 / 阶段章节 / 性能预算 / 自检）。主 spec 的附录 A 只维护**入口链接**，不展开。

**附录 A 可选**：
- **保留**：项目明确要维护未来阶段入口，新 spec 已创建或在规划中
- **删除**：用户明确不希望主 spec 提及未来工作——整节删除，不留空壳

### 3.6.5 可视化元素约束

**默认原则**：**spec 不重画 analysis 已有的图**——代码模板才是 spec 的主体。

**允许的图**：
- 代码模板旁的**小流程图**（≤10 节点），用于说明该段代码的分支/状态
- 多步 diff / 升级路径的简单时序（≤5 step）

**不允许的图**：
- 完整架构全景图（引用 analysis 即可："见 `<feature>_analysis.md §X`"）
- 跨模块全景时序图（同上）
- 方案对比类可视化（属 analysis 范畴）

**如果必须画**：复用 analysis 已定的配色/分组约定（若有），不重造——避免风格割裂。具体语法约定以 analysis 产出为准，spec 只说"沿用 analysis §图例的约定"即可，不在本 skill 预置图表语法。

### 3.7 代码模板要求

Spec 中的代码必须**可直接编译**：

1. 包含完整 `#include` 和 `namespace`
2. 标注插入位置（"在 `file.h` 约 line XX 附近"）
3. 标注参考实现（"参考 `xxx.cc:37-59` 的模式"）
4. 修改现有代码时给出前后对比
5. `[必做]` **禁止"… 其余字段同理"**——AI 不知道"同理"是什么
6. `[必做]` **对现有 API 的调用**必须能在 §2.N 参考清单中找到；未找到则替换实现方式或列为潜在隐患
7. `[必做]` **类声明的每个公开方法**都要给实现骨架（即使 stub），不允许"声明在 spec，实现回看 analysis"
8. **占位接口替换规则**：若用占位名，必须在代码块前加一小段"占位 → 真实 API"注释块（对照依据 §2.N）
9. **SWDD 测试追溯**（若已有 SWDD）：
   - Checklist 每项以 `→ **SWDD XX-N**` 结尾
   - 关键代码分支顶部加 `// SWDD 测试覆盖：XX-N（一句话场景）`
10. `[必做]` **gflag 保护就地挂接**：IO 路径 gflag 不单独成章；在 IO 入口代码模板中直接带 `if (FLAGS_xxx && !precheck(...))`；自检章节只留 checklist 提醒

### 3.8 性能预算章节

```markdown
### IO 路径增量（per-operation）
| 操作 | 新增延迟 | 占原延迟比例 |

### 内存增量
| 组件 | per-shard | per-client | 集群总计 |

### RPC 开销
| 指标 | 典型 | 极端 |
```

### 3.9 §N+1 自检章节必备子节："本 spec 范围外的实现"

显式告诉 AI"遇到以下场景不要自行展开实现"——避免 AI 看到某个 hook 点就一路实现到未来功能。

```markdown
### N+1.X 本 spec 范围外的实现
> AI 编码者遇到以下场景不要自行展开——不在本次 spec 范围。

- **不**做 XXX（说明理由，但不写"留 stage N / 后续再补"）
- **不**维护 YYY
```

**避坑**：不写"留 stage N"（spec 被删/重命名会留死链）；不写"后续再补 / TODO"（含糊边界）；用"不在本次 spec 范围"中性措辞。

## Phase 4：双向校验

### 4.1 设计文档反向校验

> Spec 细化过程中必然发现设计文档的不足。

1. Spec 确定了设计文档"待决策"的项 → **回更新设计文档**
2. Spec 修改了设计决策 → 设计文档 changelog 标注变更
3. Spec 发现新问题 → 记录到设计文档"已知限制"
4. **Spec 不是方案讨论的场所**——发现方案有问题，先回更新设计文档

### 4.2 Spec 完整性校验（四档自检）

> Spec 的真正检验：**AI 拿到这份 spec 能一发命中编码，还是一路撞墙？** 形式校验过不代表 spec 够用。发 spec 前做本节体检。

**形式校验**（易自动化）：文件清单完整 / 代码模板完整 / 测试覆盖 / 验收标准 / 跨阶段一致性 / 全文一致性（决策变更后 grep 影响点）。

**语义完备性四档**：

| 档 | 检查内容 | 判定信号 |
|----|---------|---------|
| **缺失**（会阻塞 AI） | ① §2.N 现有 API 参考清单齐全 ② 类声明方法有实现骨架（不回跳 analysis） ③ 每个 hook 挂接点有 file:line（不只说"找现有位置"） ④ 每个故障注入点给出宏名或标"待实现" ⑤ **若涉及新增持有实例**：Hosting Topology 表（§3.2.5）齐备、持有者类已 grep 回填，且 §L 有粒度判别 UT（同一 owner 共享 + 跨 owner 隔离两条对照）；项目若有 spec-lint 引擎，check 列按其 DSL 格式写 ⑥ **若 spec 跨模块复用 / 阶段并行开发**：Module Boundary 速览节（§2.0；skill §3.3）齐备且与 §2 详版 / 阶段章节代码模板签名和语义一一对应，无内部矛盾 | grep `"TODO\|FIXME\|参考 analysis\|找现有位置\|约 line"`；再人工读类声明 vs 实现；hosting 表 grep `"<待 grep>\|<填"` 是否回填；速览节签名 grep 与 §2 详版交叉对照；项目若有 spec-lint，跑 `spec-lint --spec <path>` |
| **冗余**（多处重复） | ① 同一规则不在多章节重复（gflag 保护只在 IO 挂接写一次） ② 同一概念的多层表示有对齐表 ③ 性能数字不与 analysis 全文重复，精简为"结论 + 引用" | grep 关键词在 H2/H3 出现次数 > 1 |
| **未清理**（遗留痕迹） | ① 设计文档已排除的功能未在 spec 阶段残留 ② 已改方案的旧表述清除 ③ 未来阶段引用（项目不提未来工作时）清除 ④ 注释中"留 stage N / TODO stage M" ⑤ **术语一致性**：同一概念全文命名统一；与 analysis / SWDD 术语表对齐；方案切换后的旧术语已清除或标注为历史 | grep `"stage[0-9]\|留 stage\|后续再\|TODO"`；术语部分按 analysis/SWDD 的旧术语词表逐条 grep |
| **待新增**（提升 AI 命中率） | ① 顶部有 AI 编码前置 checklist ② 有 §L 跨阶段集成与故障测试 ③ 有 SWDD 追溯（若已有 SWDD） ④ 有 Module Boundary 速览节（若 spec 跨模块复用 / 阶段间并行开发） | 检查顶部引导 / §L 位置 / checklist 格式 / 速览节是否位于 §2 首节（§2.0），紧跟 §1 总览之后、详细 Proto / 现有 API / 接入约定之前 |

**质量门禁补充检查**：
- 有状态 / 跨模块功能必须存在 §Q，且 Q1~Q7 没有空白核心行。
- 每个 lifecycle clear path 都有代码触点和测试；没有 clear path 必须写“无需清理 + 原因”。
- 每个 feature bit / proto / RPC 都覆盖声明、handler、fetch/cache、mutation hook、删除/回收和测试。
- 每个修复 review finding 的行为变更都有回归 UT，或明确写出不能本地测试的原因。

**处理**：缺失必须补齐；冗余建议合并；未清理直接清；待新增按项目成熟度决定（小项目可跳过 SWDD 追溯）。

### 4.3 潜在隐患模板

```markdown
| # | 隐患 | 触发条件 | 风险 | 缓解 |
```

隐患需具体触发条件（不是"可能有问题"），需标注是否有 gflag 可运行时关闭。

## Phase 5：代码风格规则对齐（spec 出稿前最后一步）

> spec 里的代码模板会被 AI 直接照抄成实现。如果模板违反项目 `.clang-format` / `.clang-tidy` 规则，AI 编出来必然在本地 format/lint 阶段返工，浪费一轮迭代。spec 出稿前主动对齐一次。

### 5.1 规则文件检测

对 spec 涉及的每个项目根目录跑：

```bash
ls <project_root>/.clang-format <project_root>/.clang-tidy 2>/dev/null
```

- 都不存在 → 跳过本 Phase（项目无强制风格）
- 任一存在 → 进入 5.2

### 5.2 规则提取（重点字段）

**`.clang-format`** 关注（影响代码模板可读性 + format 是否会重排）：
- `ColumnLimit` — 决定单行最大列宽，超长 trailing 注释会被多 pass 反复换行（详见 remote-vm skill）
- `IndentWidth` / `TabWidth` / `UseTab` — 缩进风格
- `BreakBeforeBraces` — 大括号位置
- `PointerAlignment` — `int* p` vs `int *p`
- `AllowShortFunctionsOnASingleLine` — 单行函数允许情况

**`.clang-tidy`** 关注（影响 AI 编码命中率，命名 / magic number 是高频踩坑点）：
- `Checks:` 行——枚举启用的 5 类（readability / modernize / cppcoreguidelines / bugprone / performance）及具体子项
- `CheckOptions:` 块尤其看：
  - `readability-identifier-naming.*` — `kCamelCase` / `UPPER_CASE` / `snake_case` 的具体绑定（常量、enum、成员、宏 各自不同）
  - `readability-magic-numbers.IgnoredIntegerValues` / `IgnoredFloatingPointValues` — 哪些数字不算 magic
  - `readability-function-size.LineThreshold` / `StatementThreshold` — 函数长度上限
  - `cppcoreguidelines-avoid-magic-numbers.*` — 与上面 readability 版本互补

### 5.3 调整 spec 中的代码模板

按提取规则反向扫一遍 spec 里所有代码块（§代码设计 / §R / §3.7 等），逐项核对并调整：

| 规则类型 | 检查 | 调整动作 |
|---------|------|---------|
| ColumnLimit | 模板里有无超列宽行（含中文 trailing 注释，2 字节计） | 超长 trailing 注释改为字段**上方**独立行注释；长字符串拼接拆行 |
| identifier-naming | 模板里的常量 / enum / 成员名格式 | 按 `.clang-tidy` 的 Case 绑定改名（如 `kMaxRetry` 而非 `MAX_RETRY`，或反之） |
| magic-numbers | 模板里有无裸数字字面量（除 `IgnoredIntegerValues` 列出的） | 抽常量 `constexpr int kXxx = N;`，并在常量旁注释含义 |
| BreakBeforeBraces / IndentWidth | 大括号位置 / 缩进 | 直接套规则，避免 AI 抄完后被 format 重排出 noise diff |
| function-size | 模板函数行数 | 超过阈值的拆函数；spec 里就拆好，不让 AI 后期被动拆 |

### 5.4 在 spec 顶部 checklist 中显式标注

§3.2 顶部 AI 编码前置 checklist 里加一行：

```markdown
- 项目风格：已按 `.clang-format` (ColumnLimit=N, ...) 和 `.clang-tidy` (identifier-naming=..., magic-numbers ignore=...) 调整本 spec 代码模板；编码者照抄即可，不要再手动改名/抽常量
```

让 AI 编码时知道 spec 里的命名 / 常量已是规则后的形态，避免画蛇添足或自作主张换风格。

### 5.5 项目无规则文件的备选

若两个文件都不存在但项目有 build pipeline 强制风格，在 spec 顶部 checklist 注明"项目风格由 build pipeline 统一处理，本 spec 未做规则对齐，编码后运行仓库规定的格式化命令"。

## Phase 6：实施完成后 spec 瘦身

> 编码完成后 spec 应从"实施 plan"转入"**行为契约 + 设计意图档案**"。代码已是唯一真相源——spec 复述实现细节只会 drift；但红线 / Conformance / 决策原因 / 跨仓契约必须保留供 CI 防回潮 + 未来 AI agent 接续工作。
>
> **触发**：每个 stage 的代码合入主分支时，**在该 stage 的 PR 里一起改 spec**（不要事后单独提"瘦身 PR"——容易被忽略，spec 会越积越重）。
>
> **不在编码进行中瘦**：实施细节还在变；瘦了再加成本更高。

### 6.1 锚点策略：禁止行号，符号名为先

> **铁律**：spec 内**禁止**写具体行号（`file.cc:123` 这种）。代码 refactor / 加注释 / 整理 import 都会让行号 drift；行号锚点失效是高频 spec 腐烂源。

| 优先级 | 锚点形态 | 示例 | 稳定性 |
|--------|---------|------|--------|
| 1（首选）| 文件路径 + **类/函数/常量名** | `src/metadata/feature_cache.{h,cc}` 内 `class ReactorFeatureCache::on_parent_change` | 高 —— 改名才失效，CI 编译期可挡 |
| 2 | 文件路径 + **段名** | `feature_cache.cc` 内 fetch 段 / poll 段 / lru 段 | 中 —— 段名跟代码注释；spec 写"以源码注释为锚" |
| 3（仅顶层枚举）| 文件路径 + 章节描述 | `protos/metadata.proto` 的 `service MetadataService` | 低 —— 但比行号好 |
| ❌ 禁止 | `file.cc:1850` / `file.h:178-198` | — | 行号 drift = 引用永久失效 |

**spec-lint DSL 配套**：
- 验证用 grep **符号存在性**（`must_match: pattern="ClassName::method"`），不是"行号是否对"
- 缺点是改名时 lint 失败；这正是优点——强制 spec 跟着改，避免无声 drift

### 6.2 三档处理（必背）

> 对每个章节问一遍："如果删掉这段，未来某个 AI 接续工作时丢失什么？"
> - 丢失契约 / 决策原因 / 红线 → **保留**
> - 丢失实现细节但 grep 代码能找到 → **替换为符号锚点**（不写行号）
> - 完全在代码里能看出来 → **删除**

| 内容类型 | 编码后处理 | 理由 |
|---------|-----------|------|
| **保留**（永久价值，CI / review / future AI 锚点）| | |
| IMMUTABLE 红线 + spec-lint DSL | 原样保留 | CI 防回潮；代码本身表达不了"以后不能改成什么样" |
| Conformance Tests 表 | 原样保留 | 行为契约 + 回归基线；UT 改名能对回 spec 编号 |
| 关键决策表 + 原因（双轨 / 替代方案否决理由）| 原样保留 | 防"重复推翻已否决方案" |
| 死角分析 / 历史问题已修小节 | 原样保留 | 代码看不出"为什么不走老路" |
| Proto / 跨仓 API 签名 / 跨模块契约 | 原样保留 | 外部消费方依赖；改了影响下游 |
| 性能预算 + 资源预算 | 保留并随实测校准 | 后续优化基线 |
| 自检 checklist / AI 陷阱（**v2 增量 + 长期契约级**）/ 已知限制 / 范围外 | 保留——已被 spec-lint DSL 挡的通用陷阱可删（见 §6.3 #4）| review 工具 + 长期 maintenance 文档 |
| Hosting Topology 持有者结论 | 保留（用符号名，不写行号）| 粒度错位的长期防回潮锚点 |
| Module Boundary 速览节（接口契约）| 保留——只更新已交付的符号名、删除已废弃的接口；签名形态不动 | 消费方 / 未来 AI 接续工作时的入口；spec 整个生命周期都用得上 |
| **契约级优化**（生产实施中验证有效、删除会让性能 / 正确性退化的小判断）| 单独标注"**契约级保留，禁止重构移除**" + spec-lint DSL 强制 | 例：rename hook 内 `parent_feature_id != INVALID_ID` 防同 parent 内改名误触；删了会无声退化 |
| **替换为符号锚点**（代码是真相源；锚点不写行号）| | |
| 类声明 / 常量段 / 公开 API 列表 | `src/.../xxx.h` 内 `ClassName` / 常量名 + 一行职责说明 | 类签名漂移由编译期挡，spec 不必复述 |
| 实现段（函数体逻辑）| `src/.../xxx.cc` 内 `<段名>` 段（resolve / walk / fetch / poll / lru / snapshot 等）| 段落注释清晰即可，spec 不复述实现细节 |
| metric 符号声明 / proto enum 枚举展开 | "见 `xxx_metrics.h`" / "见 `protos/xxx.proto`" | 符号增减由代码 grep |
| `module_dump` / hook 等单点接入代码 | `xxx.cc` 内 `HelperClass::handle_xxx` → `on_yyy` | 接入点是代码事实 |
| **删除**（纯实施细节）| | |
| 函数体（循环 / 分支 / 状态机内部）| 整段删 | 代码是真相源；保留只会 drift |
| UT 脚手架代码（SetUp / mock 桩 / fake clock）| 整段删，保留必备用例描述（一行一用例）| 同上；用例**描述**保留作回归基线 |
| metric / bvar 定义 .cc | 整段删 | 同上 |
| 已交付的"代码量 / 难度 / IO 路径影响"评估表 | 删（保留"风险 + 缓解"，那是契约级）| 评估是写 spec 时的预算，已交付后无意义 |
| 顶部 AI 编码前置 checklist 中**已交付** stage 的 grep 命令 | 删（避免误导后来 AI 走已完成的流程）| 仅保留对未实施部分有效的提醒 |

### 6.3 章节合并策略（避免重复）

**问题**：spec 多个 § 都有"该 stage 的 file:line 表"——瘦身后产生 N 张零散表，章节间重复。

**正确做法**：

1. **顶部建一张"📚 已交付实施索引"**（紧跟 📦 实施状态表后）—— 集中列已交付的所有文件 + 公开符号 + 段名 + 关键常量
2. **各 § 内不再重复列已交付内容**——改为"已交付实现见 📚 实施索引"一句话引用，只保留 v2 增量 / 风险 / Conformance 引用
3. **跨 § 同名符号只在 📚 索引里出现一次**——避免"§3.4 列了 walk_chain，§3.5 又列一遍"

**索引内每条只写**：文件路径 + 类/函数/段名 + 一句职责。**不写**：行号、commit hash（commit 已在 📦 实施状态表）、字段长度数字（已在红线表）、参数列表（让读者读源码）。

### 6.4 操作流程（每 stage 实施完成时）

1. **顶部加 / 更新"📦 实施状态表"**（紧跟 IMMUTABLE / Hosting Topology 之后）：

   ```markdown
   ## 📦 实施状态

   | 阶段 / 子项 | 状态 | 主 commit | 实现位置（符号名）|
   |------------|------|----------|------------------|
   | stage a 主体 | ✅ 已交付 | <hash> | `src/.../xxx.{h,cc}` 内主要符号一句话列出 |
   | stage a 子项：<待重写 / 待对齐项> | 🚧 待 ... | — | <说明>|
   | stage b | 🚧 待实施 | — | — |
   ```

   `<hash>` 用主合入 commit（不是中间 fixup）；多个 commit 列主功能那条 + 备注 clang-tidy 整理。**子项粒度**：当某 stage 内部分功能已交付、部分待重写（如 v2 替代 v1）时，单独列一行——避免"已交付 + 待施工"混在一格。

2. **顶部加"📚 已交付实施索引"**（按 §6.3 合并策略）。

3. **该 stage 的章节按 §6.2 三档处理**：
   - 章节标题 / 编号**不变**（避免破坏交叉引用）
   - 章节体瘦身：删代码模板，改为"已交付见 📚 索引；本节仅留 v2 增量 / 风险 / UT 描述"
   - 保留该 stage 的 v2 增量代码模板 / Conformance / 验收 checklist / 评估的"风险 + 缓解"

4. **顶部"AI 编码前置 checklist"过滤已交付阶段的提醒**——已交付的 grep 命令直接删；只留对未实施部分有效的引导。在 checklist 顶部声明"仅对未实施部分生效；已交付见 📦 实施状态表"。

5. **AI 陷阱表瘦**：已被 spec-lint DSL 自动挡的通用陷阱（mutex / 全局单例 / std::thread 等）从陷阱表删除——DSL 已嵌入 IMMUTABLE 表的 check 列就够。陷阱表只保留：
   - v2 增量编码相关的（visitor 同步等 / inflight 泄漏 / sleep 等 prefetch 等）
   - **契约级优化保护**（如 hook 触发条件防止重构误删）
   - 不易机器化的 review 提问

6. **spec 末尾加 Changelog 一行**：

   ```markdown
   ## Changelog
   - <YYYY-MM-DD>：stage <N> 实施完成（commit <hash>）；spec 该 stage 章节转参考态（删代码模板，保留契约 / 红线 / 决策）
   ```

   **重大锚点策略变更也记**：如"删 file:line 行号引用，改文件 + 符号名"是文档生命周期级事件，写一行说明。

7. **跑一遍 spec-lint**（若项目集成）：DSL 用符号 grep 验证（不验证行号），失败说明改名了——同步更新 spec 索引中的符号名。

### 6.5 何时**不**瘦身

| 场景 | 处理 |
|------|------|
| 该 stage 已实施但**消费方未接入**（如基础设施已交付，下游消费方还没接入）| 保留消费方接入小节的代码模板 + 示例（消费方 AI 还要照着写），其他实施细节按 §6.2 瘦 |
| 同一 stage 的 v2 增量正在实施（v1 已交付，v2 增量进行中）| 把章节拆"v1 已交付（瘦身后）"+ "v2 增量（保留代码模板）"两块；不要混写 |
| spec 涉及多仓库，本仓已实施但他仓未实施 | 本仓部分按 §6.2 瘦；他仓部分保留契约 + 代码模板（他仓 AI 还要用） |
| 红线 / Conformance / 决策章节 | **永远不瘦**；即使每行都"读起来很显然"，那是因为它们已经成了大家的常识——但这恰恰是它们存在的价值 |
| **契约级优化**已生效但易被忽视的小判断 | 不仅保留，还要在多处冗余固化（实施状态表 + 实施索引 + AI 陷阱表 + spec-lint DSL）—— 单点保留太脆弱，重构者可能一个 PR 就改没了 |
| 已交付 stage 的接口需要 breaking change（改签名 / 改语义 / 删接口）| **不属于 P6 瘦身的范畴**——走"升级正式变更"流程：发起评审 + 同步消费方 spec + 更新 §2.0 速览 + 更新 IMMUTABLE 接口稳定性红线；接口稳定后再按 §6.2 三档处理 |

### 6.6 自检

- [ ] 顶部"📦 实施状态表"齐全，每行 commit hash 可点 / 可 grep
- [ ] 顶部"📚 已交付实施索引"集中——各 § 不再重复列已交付的"file:line 表"，改为引用索引
- [ ] **零行号引用**：`grep -nE '\.cc:[0-9]+|\.h:[0-9]+|line [0-9]+|约 line' <spec>` 应**完全无命中**
- [ ] 已交付 stage 的代码模板已删；章节体仅保留契约 / 决策 / 陷阱 / 自检 / 限制
- [ ] 顶部 AI 编码前置 checklist 不再列已交付阶段的 grep 命令
- [ ] AI 陷阱表已瘦——通用约束（mutex / 单例等）由 spec-lint DSL 挡，陷阱表只留 v2 增量 + 契约级优化保护
- [ ] spec-lint DSL 引用的**符号名**仍然有效（grep 不空）；改名导致 lint 失败时同步更新 spec
- [ ] 红线 / Conformance / 决策原因 / 死角分析 / 跨仓契约 / 性能预算 / AI 陷阱 / 已知限制 这八类章节**未被动**
- [ ] 契约级优化（如 hook 触发条件防误删）在多处冗余固化（状态表 / 索引 / 陷阱 / DSL 至少各 1 处）

> **不卡总行数**：实战中 P5 → P6 行数变化随 spec 复杂度 / 已交付 stage 数 / v2 增量保留量差异极大（-20%~-50% 都见过）。判断瘦得到不到位用上面的清单——**每一项打勾代表一个具体维度**，比"砍 X% 行数"更有指导意义。如果想要单一数字，可以参考 `git diff --stat <bef>..<aft> -- <spec>` 看净删除量是否合理。

### 6.7 反模式（瘦身常见误操作）

| 触发场景 | 正确做法 |
|---------|---------|
| 写具体行号（`file.cc:123` / `file.h:178-198`）| 用"文件 + 类/函数/段名"；行号会 drift |
| 多个 § 各自保留"已交付 file:line 表" | 合并为顶部"📚 已交付实施索引"单表，§ 内引用 |
| 把 IMMUTABLE 红线 / Conformance 表也删了（"代码里都有了"）| 永远保留——这两类是"代码本身表达不了"的契约 |
| 删了死角分析 / 替代方案否决理由（"不再讨论了"）| 永远保留——防止后人重新踩同坑 |
| 删了"契约级优化"小判断（如 hook 触发条件）| 单点保留太脆弱；要在多处冗余固化（状态表 / 索引 / 陷阱 / DSL）|
| 章节标题 / 编号也改了（趁瘦身重新组织）| 标题/编号不动；只瘦内容；交叉引用不能断 |
| 等"全部 stage 完成再统一瘦"| 单 stage 完成时就瘦；攒一起做容易拖延 + 上下文丢失 |
| 瘦完没回填符号锚点（写"实施位置：见代码"）| 必须给具体类名 / 函数名 / 段名 |
| 把 spec 整份删掉（"代码已合入，spec 没用了"）| 错——契约部分仍是 CI / review / future-AI 锚点；只瘦不删 |
| spec-lint DSL 还在用 `must_match` 校验行号 | 改用符号名 / 类名 grep；行号 drift 后 DSL 会假阳失败 |

## 约束

1. Spec 不做方案选型，发现问题先回更新设计文档
2. Spec 修改任何决策必须同步设计文档
3. 架构假设必须验证
4. 需求明确要求的功能不能放"可选"阶段
5. 每阶段有独立编译 + 测试命令
6. IO 路径修改必须有 gflag 开关
7. 新增存储时评估对现有组件的影响
8. 性能评估必须包含极端规格场景
9. 所有文件引用使用项目相对路径
10. 主 spec 仅含本次阶段；未来阶段独立文件
11. 输出目录遵循仓库现有约定
12. 管理面辅助能力必须标"非系统依赖"

## 反模式

按**元类别**组织。每类下以"触发场景"说明。

### 1. 代码真实性（核心原则 #3 违反）
| 触发场景 | 正确做法 |
|---------|---------|
| 调用推测的 API 名 / 类方法只声明让读者回跳 analysis / 修改文件不给行号 / 代码模板不完整（"其余字段同理"） | §2.N 参考清单列 file:line + 真实签名；占位名必须标替换规则；每方法给完整骨架（stub 也要）；修改点给 file:line；代码模板可编译 |

### 2. 范围与边界（核心原则 #4 违反）
| 触发场景 | 正确做法 |
|---------|---------|
| 设计文档排除的功能混入 spec 阶段 / 未来阶段 API 进接口章节 / 所有功能塞一个阶段 / "留 stage N" 措辞 / 附录 A 保留空壳 | 不覆盖的功能只在"本 spec 范围外"列一句话（中性措辞，不提具体后续阶段名）；未来阶段独立文件或直接不写；最小集开始逐阶段扩展；用户明确不提未来工作时整节删除 |

### 3. IO 安全 / 辅助能力定位
| 触发场景 | 正确做法 |
|---------|---------|
| IO 路径修改无 gflag / gflag 保护单独成章与挂接代码分离 / 辅助工具写成主路径硬依赖 | IO 入口代码模板中直接带 `if (FLAGS_xxx && ...)`；自检章节只留 checklist 提醒；辅助能力独立子节标"非系统依赖" |

### 4. 决策同步 / 形式校验
| 触发场景 | 正确做法 |
|---------|---------|
| 决策变更只改 spec 不回改设计 / 跳过设计自检直接写 spec / 性能用"可能""大概" / 形式校验过就认为够用 | 发现问题先回设计文档；先确认 analysis 自检通过；性能给具体数值 + 占比；发 spec 前按 P4.2 四档自检才算闭环 |

### 5. 文档卫生
| 触发场景 | 正确做法 |
|---------|---------|
| 方案对比进 spec / 文件引用用本地绝对路径 / spec 位置写死 `docs/design/<module>/` | 方案对比回设计文档；项目相对路径；先看仓库现有约定（`docs/spec/` 优先） |

### 6. 实施完成后维护（Phase 6 违反）
| 触发场景 | 正确做法 |
|---------|---------|
| 已交付 stage 仍保留完整代码模板（spec / 代码两份维护，drift 风险）/ 攒"全部完成再统一瘦" | 每 stage 合入时在该 PR 里走 Phase 6.2 三档处理：保留契约 / 替换为符号锚点 / 删除实施细节 |
| 瘦身时把红线 / Conformance / 决策 / 死角分析 / 契约级优化也删了 | 永远保留——这些是代码本身表达不了的契约；契约级优化（如 hook 触发条件）要多处冗余固化 |
| 写具体行号（`file.cc:123` / `file.h:178-198`）—— 行号会随 refactor drift 失效 | **禁止行号**；只用文件 + 类/函数/段名（符号名稳定，CI 编译期可挡）|
| 多个 § 各自保留"已交付 file:line 表"，章节间重复 | 合并为顶部"📚 已交付实施索引"单表；§ 内引用 |
| spec-lint DSL 用行号校验（`must_match: pattern="...:1850"`）| 改用符号名 / 类名 grep 验证存在性；改名失败 = spec 同步更新提醒 |
| Module Boundary 速览节塞详细 proto field number / N 步接入 checklist（应在 §2 详版）/ 速览节签名与 §2 详版不一致 | 速览节放签名 + 语义 + 失败行为 + 调用约定；field number / 接入 N 步留 §2 详版；P4.2 一致性自检挡内部矛盾 |
