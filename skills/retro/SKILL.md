# Retrospective（复盘起草与评审）

把"已发生的事"沉淀成可被团队复用的知识。强制分级表达——分清**已确认 / 假设 / 未解之谜**、**workaround / 根因修复**——避免把临时手段当成结案。

## 调用形态

```
$retro draft <type> [--input <素材文件>]
$retro review <retro-file>
```

`<type>` 取值：

| type | 适用场景 | 章节侧重 |
|---|---|---|
| `incident` | 故障 / 性能事故 / 客户现场问题 | 反直觉信号独立小节、对照实验、workaround 边界 |
| `feature-bug` | 一个 FR / 新功能反复出 bug，需要找系统性原因 | bug timeline 表、根因分类、测试覆盖盲区、流程缺口 |
| `project` | 项目 / 迭代 / 大版本复盘 | 里程碑偏差、决策回看、沟通/工具/排期问题 |
| `decision` | 单一关键决策的复盘 | 决策时点、当时信息、反事实分析 |

未给 `<type>` 时，先和用户确认。

`--input` 不给时进入对话式起草模式（打印质询清单，让用户逐项贴/答）。

## AI 读法约定

> **规则标签**：
> - `[必做]` — 硬约束，省略会导致复盘失去价值或返工
> - `[推荐]` — 默认执行；不适用时一句话说明理由可跳过
>
> **产出文档倾向**：表格 > 列表 > 段落；**结论 > 阐述**；callout 承载关键判断和反直觉信号。
>
> **长度预算**（参考）：复盘主文典型 ≤ 600 行；超过时把详细数据 / 长 log 抽附录。

## 核心原则

1. `[必做]` **诚实分级**：每条断言要明确属于「已确认 / 假设 / 未解之谜」之一，不允许混写。"这是 X 导致的"是结论，"这可能是 X 导致的"是假设，"为什么会 X 我们还不知道"是未解之谜——三种说法在文档里要可视化区分。
2. `[必做]` **workaround vs 根因修复要标清**：若当前修复是 workaround，TL;DR 和"当前行动"章节都必须显式标注；同时必须有"为什么说这是 workaround"和"对哪些扰动源没有保护"两段。
3. `[必做]` **未解之谜不能含混**：每个未解问题都要写「为什么重要 + 验证手段」。"再调查"、"待跟进"、"加强监控"是空话。
4. `[必做]` **行动项必须可独立验证**：每条行动项有"做什么 + 怎么知道做完了"。"加强 X" / "提升 Y" / "优化 Z" 不达标，必须改成"在 dashboard A 看到指标 B 持续 N 天" / "提交 MR XXX 完成"。
5. `[推荐]` **反直觉信号独立成节**：故障复盘中"直觉上应该升却降 / 应该报警却安静"的信号往往最有诊断价值，独立小节强调。
6. `[推荐]` **对照实验优于事后归因**：能提供"必复现 vs 不复现"的差异对照是黄金证据；只有事后日志的归因要谦虚标"假设"。
7. `[推荐]` **教训独立成 callout**：每条教训一句主旨 + 一段解释，便于团队转载分享。

## 通用骨架（所有 type 共用）

复盘主文按以下顺序组织（具体章节内容由 type 分支决定）：

```
TL;DR callout（核心结论 — 一眼看清现象 / 已做的修复 / 是否是 workaround）
§1 事实陈述（环境 / 现象 / 数据；不做归因）
§2 根因分析（已确认 / 假设 / 未解之谜，三栏分清）
§3 当前行动 / 修复（明确标 workaround vs 根因修复 + 边界）
§4 教训（按角度分类，每条独立 callout）
§5 行动项（已完成 / P0 本周 / P1 月度 / P2 季度，每条可独立验证）
末尾 slogan callout（一句话总结）

附录（按需）
  A. 完整 log / metric 截图
  B. 详细对照实验数据
  C. 已否决的修复方向（带根因）
```

> **章节顺序硬规则**：§1 只摆事实，**禁止在 §1 做归因**——归因留给 §2，避免读者被先入为主的解释带偏。

## Callout 语义体系（飞书 / Markdown 通用）

复盘文档的 callout 是结构化信号，emoji 不能乱用：

| Emoji | 语义 | 何时用 |
|---|---|---|
| 📌 | 核心结论 / 长期方向 | TL;DR、章节小结、slogan |
| 📝 | 解释性补充 | 对表格/数据的附加说明 |
| ❗ | 反直觉信号 | "应该升却降"、"应该报警却安静" |
| ✅ | 已确认事实 / 已完成 | 实验证据、完成的行动项、好对照 |
| ❌ | 反例 / 失败对照 / 不要做 | 坏对照、被否方向 |
| ❓ | 未解之谜 | 章节标题或具体未解问题 |
| 💡 | 假设 / 第一性原理 / 启发 | 未证实的机制假设、设计原则 |
| ⭐ | 长期方向 | 季度级或更远的改进 |

`[必做]` 文档中**至少**出现：1 个 📌（TL;DR）、若干 ✅（已确认事实）、若干 💡（假设）、若干 ❓（未解之谜——除非真的全已解释）、1 个 📌（末尾 slogan）。如果一份故障复盘里**一个 ❓ 都没有**，多半是把假设当成了结论，要重审。

## Draft 模式

### 步骤 1：素材入口

- 有 `--input <file>` → 读取该文件，提取已有结构化信息
- 无 `--input` → 打印 type 对应的质询清单（见下），让用户逐项贴/答

### 步骤 2：质询清单（按 type 分支）

`[必做]` 缺失项不得脑补——明确标 `⚠️ 待补` 留在文档里，宁可让文档显得"不完整"，也不要用编造的数据/解释填空。

#### `incident` 类型质询清单

| 维度 | 必填 | 提示 |
|---|---|---|
| 测试 / 生产环境配置 | 是 | 硬件型号（特别是少见的）、软件栈版本、拓扑、网络模式 |
| 工作负载与故障现象 | 是 | 压力模型（QPS / size / 并发）、错误码原文、是否自愈、退化幅度 |
| 多层观察数据 | 是 | 每层都要好/差时段对照值（延迟 / 带宽 / 错误率 / 内核计数器） |
| **反直觉数据点** | 是 | 直觉上"应该升却降"的信号，单独列。**最易漏的一项** |
| 对照实验记录 | 推荐 | 至少一组"必复现 vs 不复现"，差异变量单一可控 |
| 修复尝试 | 是 | 配置 diff、是否实时生效、做了多久 stress、覆盖了哪些扰动源 |
| **诊断盲区** | 是 | 哪些数据没拿到 / 拿到但解释不通 / 哪些假设没法证实 |

#### `feature-bug` 类型质询清单

适用于"这个 FR 上线后陆续出了 N 个 bug，想找系统性原因"。

| 维度 | 必填 | 提示 |
|---|---|---|
| 功能背景 | 是 | FR 编号 / 上线时间 / 设计文档链接 / 主要改动模块 |
| Bug 时间线 | 是 | 表格：日期 / 现象 / 严重度 / 修复 commit / 暴露场景 |
| 每个 bug 的根因分类 | 是 | 设计缺陷 / 编码错误 / 测试盲区 / 文档不清 / 评审遗漏（多选） |
| 测试覆盖盲区 | 是 | UT / IT / 长稳 / 客户场景 各覆盖了什么、漏了什么 |
| 流程缺口 | 是 | 设计评审 / 代码评审 / 测试评审 / 灰度策略 哪环出了问题 |
| **共同模式** | 是 | 多个 bug 是否指向同一个根本原因（架构 / 抽象 / 心智模型） |
| 类似功能的 bug 率对比 | 推荐 | 如果有可比对照（同模块其他功能 bug 率），说明本功能是否异常 |

#### `project` 类型质询清单

| 维度 | 必填 | 提示 |
|---|---|---|
| 项目目标与最终交付 | 是 | 计划交付 vs 实际交付，差异定量 |
| 里程碑与偏差 | 是 | 表格：milestone / 计划日期 / 实际日期 / 偏差天数 / 原因分类 |
| 关键决策点 | 是 | 哪几个决策对结果影响最大，当时基于什么信息做的，现在看怎么样 |
| 沟通问题 | 推荐 | 跨团队信息不对齐的具体事件 |
| 工具 / 流程问题 | 推荐 | 工具不顺手 / 流程绕弯 的具体事件 |
| 估算偏差分析 | 推荐 | 哪类工作系统性低估 / 高估 |

#### `decision` 类型质询清单

| 维度 | 必填 | 提示 |
|---|---|---|
| 决策内容 | 是 | 选了什么、否了什么、什么时点决策的 |
| 当时的信息 | 是 | 决策时已知什么、不知道什么、有哪些假设 |
| 决策标准 | 是 | 当时用什么标准选的（成本 / 时间 / 风险 / ...） |
| 实际结果 | 是 | 决策落地后发生了什么，与预期的差异 |
| 反事实分析 | 是 | 如果选了被否的方案，现在会怎样？这是评估"决策质量 vs 运气"的关键 |
| 信息盲区 | 是 | 当时哪些关键信息我们其实可以拿到但没拿到？ |

### 步骤 3：起草

按通用骨架 + type 侧重写出主文。强制要求：

1. `[必做]` `§1` 只摆事实——发现自己在 §1 写"这是因为..."就停下来移到 §2。
2. `[必做]` `§2` 用三栏结构（已确认 / 假设 / 未解之谜）——不允许混写。模板：

   ```markdown
   ## §2.1 已确认的因果链
   <mermaid 或表格，标出哪一步有实验证据>

   ## §2.2 假设（未完全证实）
   | 假设 | 机制 | 支持证据 | 反对证据 |

   ## §2.3 仍未解释的关键事实
   | 未解问题 | 为什么重要 | 验证手段 |
   ```

3. `[必做]` `§3` 若是 workaround，**TL;DR 和章节标题都要标**。模板：

   ```markdown
   # §3 当前修复（实质是 workaround）

   ## §3.1 配置 / 代码变更
   <grid> 双栏对照（原 vs 新）

   ## §3.2 为什么说这是 workaround，不是根本修复
   - 没有解释 X
   - 对 Y 类扰动源没有保护
   - Z 矛盾未解释
   ```

4. `[必做]` `§5` 行动项分级 + 可验证：

   ```markdown
   <callout emoji="✅">已完成</callout>
   - [x] <动作> — <可验证标志：commit / dashboard / 实验编号>

   <callout emoji="📌">P0（本周内）</callout>
   - [ ] <动作> — <验收标准>

   <callout emoji="📌">P1（月度，对治脆弱性）</callout>
   - [ ] ...

   <callout emoji="⭐">P2（季度，系统性改进）</callout>
   - [ ] ...
   ```

### 步骤 4：输出位置

- 默认：`docs/retro/<topic>/<YYYY-MM-DD>_<type>_retro.md`
- 用户自定义路径就用用户的
- 同目录下可放 `<topic>_data.md`（详细数据）/ `<topic>_research.md`（背景调研）作为附录，主文用相对路径引用

### 步骤 5：自检（draft 完成前）

| 检查项 | 通过标准 |
|---|---|
| 三栏分清 | §2 没有混写"已确认"和"假设" |
| workaround 标注 | 若是 workaround，TL;DR + §3 标题 + §3.2 边界说明三处都有 |
| 未解之谜量化 | 每个 ❓ 都有"为什么重要 + 验证手段" |
| 行动项可验证 | 每条行动项有"怎么知道做完了" |
| 反直觉信号被记录 | 故障复盘有 ❗ 章节或 callout（除非真的没有反直觉信号） |
| 教训成 callout | 每条教训独立 📌 callout，不混在正文段落里 |
| Callout 体系完整 | 至少有 📌 TL;DR / ✅ 事实 / 💡 假设 / ❓ 未解 / 📌 slogan |

发现不通过项时**当场修**，不要留到 review 模式才发现。

## Review 模式

接收一份已有复盘文档（自己写的草稿、他人的、AI 生成的），输出 **P0~P3 分级 todo list**——不写"看起来不错"。

**输出位置**：与被评审文档同目录，`<原文件名>_review_round_<N>.md`（N 从 1 起递增）。

### 评审 5 层 checklist

#### L1：事实可信度（5 分钟）

**问**：每个数据是否有来源？

**checklist**：
- 关键数据有 log 引用 / metric dashboard 链接 / 实验编号
- "X 倍"、"N ms" 这类数字能定位到来源
- 引用的代码 / 配置 / log 段有 file:line 或时间戳

**输出**：`| § | 断言 | 来源 | 状态 |`，状态 = `✅ 已落实 / ⚠️ 模糊 / ❌ 缺失`

#### L2：分级诚实（最重要的一层）

**问**：「已确认 / 假设 / 未解之谜」是否分清？有没有把假设当成结论？

**做法**：grep 全文，找以下"虚假确定性"信号：

| 信号词 | 追问 |
|---|---|
| "因为...所以..." | 这是因果链的哪一步？是实验证实的还是推理的？ |
| "明显是 X 导致的" | 实验对照在哪？还是只是"看起来像"？ |
| "是 X 引起的"（无证据） | 该段应该改成 "假设是 X" 或挪到 §2.2 |
| "这是个 workaround" 没出现在 TL;DR | TL;DR 漏标，读者会误以为是根因修复 |
| "未来会..." / "后续优化" | 应该是行动项 §5，不该埋在 §2/§3 |

**输出**：`| § | 现状描述 | 应改为 | 严重度 |`

#### L3：未解之谜量化

**问**：每个 ❓ 是否给了"为什么重要 + 验证手段"？还是含混带过？

**反模式**：
- "再调查一下"、"待跟进"、"加强监控"——空话
- "可能跟 X 有关"——既没说"为什么这个假设值得验证"，也没说"怎么验证"
- 未解之谜没有对应行动项

**输出**：每个未解之谜独立一条 todo，标 P0/P1：

```
[P1] §2.3 BS 800ms 延迟来源未解释
  - 为什么重要：是"故障期延迟在哪堆积"的最大盲区
  - 缺失：没有给具体验证手段
  - 建议：补"BS worker 加细粒度时延打点 + 对比好/差时段队列长度"
```

#### L4：行动项可验证

**问**：每条行动项是否有"怎么知道做完了"？

**checklist**：
- 动作具体到模块 / 配置 / commit
- 有验收标志（dashboard 指标 / log 输出 / 实验通过）
- 不是"加强 X"、"优化 Y"、"持续关注"

**做法**：把不达标的行动项重写或拆分。例如：

| 现状（不达标） | 重写后 |
|---|---|
| "加强网络监控" | "在网络 Grafana board 增加拥塞、pause 和重复请求 panel，回归集群连续观察一周" |
| "考虑改进 RPC 框架" | 拆成 P1："对比直连路径与完整 RPC 栈，输出差异点列表"；P2："基于差异点修复优先级最高的三项" |

#### L5：反直觉信号 / 盲区检查

**问**：故障复盘是否记录了反直觉信号？feature-bug 复盘是否找了"共同模式"？project 复盘是否做了反事实？

**reasonable absence 也接受**：如果真的没有反直觉信号，可以没有 ❗ 章节——但要在 review 中确认是"真没有"还是"漏写"。做法：

- 故障复盘：列文档中提到的所有指标，问"哪些方向变化和直觉相反"
- feature-bug 复盘：bug 列表过一遍，问"这些 bug 是不是都来自同一个心智模型错误"
- project 复盘：决策列表过一遍，问"哪几个决策如果反过来选，结果会更好吗"

### Review 输出格式

```markdown
# 复盘评审 round N — <retro-file>

## 总评
- 文档类型：incident / feature-bug / project / decision
- 整体诚实度：✅ / ⚠️ / ❌（基于 L2 结果）
- workaround 边界标注：✅ / ⚠️ / N/A

## 待办（P0 阻塞，P1 必处理，P2 改进，P3 nice-to-have）

### P0
- [ ] [§X] <发现> — <建议改法>

### P1
- [ ] ...

### P2
- [ ] ...

### P3
- [ ] ...

## 已确认良好的部分
（不复述文档，只列"特别值得保留"的设计或表达，给作者正反馈）

## 评审者守则提示
- 本评审依据 L2 标尺，特别关注是否把假设当结论
- 不替作者决策；P0/P1 给出建议改法但最终由作者吸收
- 不直接改写复盘主文；输出独立 review 文件
```

## 反模式

按元类别组织：

### 1. 假装结案
| 触发场景 | 正确做法 |
|---|---|
| 当前是 workaround 但 TL;DR 写"已修复" | TL;DR 必须显式标 "实质是 workaround"，并指向 §3.2 边界说明 |
| 把"暂时不复现"等同于"根因解决" | §3.2 必须列"对哪些扰动源没有保护"、"哪些矛盾没解释" |
| 未解之谜全藏在脚注 / 附录 | §2.3 是主文必备章节，未解之谜要正面摆出 |

### 2. 虚假确定性
| 触发场景 | 正确做法 |
|---|---|
| 把推理当实验证据 | 推理写在 §2.2"假设"，标 💡；只有对照实验通过才能进 §2.1"已确认" |
| 单一日志归因（"看到 X 错误所以是 X 导致的"） | 至少给一组反例对照（"无 X 错误的时段是否也有同样现象"） |
| 因果链最后一跳含混（"X → ? → 结果"） | mermaid 图标灰色 / 加 (?) 注明该跳是假设 |

### 3. 行动项空话
| 触发场景 | 正确做法 |
|---|---|
| "加强监控 / 优化 X / 关注 Y" | 改写成"在 dashboard A 加 panel B" / "提交 MR XXX" / "实验通过 = ..." |
| 行动项无优先级 | 必须分 已完成 / P0 本周 / P1 月度 / P2 季度，不允许混合 |
| 行动项无 owner（多人项目） | 每条至少标责任人（个人复盘可省） |

### 4. 反直觉信号被埋没
| 触发场景 | 正确做法 |
|---|---|
| 只列"和故障一致"的正向证据 | 把"和直觉相反"的信号独立 ❗ callout，常常这才是诊断关键 |
| 数据只给故障期值，不给好时段对照 | 多层指标给好/差时段对照表，反向变化的指标要重点标 |

### 5. 教训扁平化
| 触发场景 | 正确做法 |
|---|---|
| "这次教训是要小心 X" 写一句话 | 每条教训独立 📌 callout：一句主旨 + 一段解释（为什么、什么时候适用） |
| 教训只针对本次 bug | 抽出"元教训"（流程 / 心智模型 / 设计原则层面），便于跨场景复用 |

### 6. 评审走过场（review 模式专属）
| 触发场景 | 正确做法 |
|---|---|
| review 输出"看起来不错"或泛泛建议 | 必须落到 §X / 具体段落，给 P0~P3 分级 |
| review 直接改写复盘主文 | 评审者不是合著者；输出独立 review 文件，由作者决定吸收 |
| review 没有 L2 诚实度判断 | L2 是复盘评审的核心，必须给 ✅/⚠️/❌ 总评 |

## 与其他 skill 的边界

| 邻近 skill | 区别 |
|---|---|
| `$design-analysis` | 面向"未发生的事"——做新方案；retro 面向"已发生的事"——沉淀经验 |
| `$design-review` | 评审"设计文档"；retro review 评审"复盘文档"。两者 checklist 不同：design-review 7 角度找架构漏洞，retro review 5 层找诚实度漏洞 |
| `$cicd-check` | 面向"具体一次 CI/CD 失败的根因定位"，是诊断动作；retro 是诊断之后的沉淀文档 |
| `$quarterly-report` | 面向"自己干了什么"的活动汇总；retro 面向"为什么这样 / 下次怎么办"的反思 |

需要把复盘发布到飞书时，引用 `$feishu-doc` 处理 callout / mermaid / grid 的渲染细节——本 skill 只产出 Markdown 主文。
